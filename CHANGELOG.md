# Changelog

All notable changes to RivetCore. Semantic versioning.

## 1.0.0-rc.24 (per-OS check targeting, stale check cleanup; migration 0032)

A Windows PC (mwa) was given the Linux-only service checks (`svc_chronyd`, `svc_cron`, `svc_sshd`, ...), reported "service X not found" (`fail`) and raised alerts. The schedule is one list for every device and delivery ignored which OS a check was for. Additive to the frozen protocol ([PROTOCOL.md](docs/rmm/PROTOCOL.md) 3.2.8); old agents and the golden transcripts are unaffected.

- **`os` on a check definition** (`windows`, `linux`, left out or `any` = both) in the schedule (`ChecksValidator`, kept through save and load, other values rejected with a clear message) and in policy check templates (`check.<key>`, "applies to"). New `Checks\RmmChecks` (`forOs()`, `normalizeOs()`).
- **Delivery filters by the device's OS** (`RmmSettings::signedChecks($caps, $os)`, `signCheckList(..., $os)`, `EffectiveConfig::compose(..., $os)`; enrollment, check-in, policy path). The signature covers each delivered entry, `os` included; an entry without `os` is unchanged byte for byte. The policy `version` is computed after the filter. Technician policy view shows `os`.
- **Stale cleanup.** A check key no longer delivered to a device loses its `endpoint_agent_checks` (and `rmm_check_eval`) row and its open alert is resolved ("This check no longer applies to the device", system, reason `not_applicable`; no ticket, no re-alert; a still-delivered check is untouched). Lazy at check-in through the new Core table `rmm_device_checkset` (migration `0032_rmm_check_set`): one primary-key read, work only when the delivered set changed. `RmmModule::reconcileChecks(?int)` is the one-off backfill for all live devices. Server-reported keys (`log.rule_*`, `change.rule_*`, `patch.*`) are never cleaned; the first sight of a device only cleans schedule keys that are not delivered, and a check dropped only for a missing `check:<type>` capability is kept.
- **Agent.** Ignores a delivered check for another OS (`checksForOS`); the service check takes `missing` (`fail` default, `warn`, `ignore`) on both platforms.
- **Vectors.** New `agent_check_os_vectors.json` (signed entries with `os`, delivered keys per OS), replayed by PHP and Go; the earlier files keep their bytes.
- **Tests.** PHP `CheckOsTargetingTest` (unit 5, integration 6: a Windows and a Linux device get different signed lists, stale cleanup and alert resolution, no flapping, server keys kept, backfill, alerting record), Go `TestChecksForOS`, `TestCheckOSVectors`, `TestServiceMissingParam`. Harness fix: it now applies migration 0030 on a fresh scratch database.
- **Known limits.** With queued ingest (`ingest_mode` queued) a result for a stale key that was still buffered when the list changed can re-create the row after the cleanup; the next delivered-set change or `reconcileChecks()` clears it. Not run: any Windows host.
- **Editions.** See UPGRADING.md ("Adopting per-OS check targeting"): migration 0032, set `os` in the schedule builder, call `reconcileChecks()` once.

## Unreleased (build host script for local agent builds; server side not built yet)

`endpoint-agent/scripts/build-host.sh` (+ `build-host.service`, `build-host.timer`, `build-host.conf.example`, [docs/rmm/BUILD_HOST.md](docs/rmm/BUILD_HOST.md)) implements the build host half of [BUILD_HOST_PROTOCOL.md](docs/rmm/BUILD_HOST_PROTOCOL.md): poll, claim, clean temporary worktree of an allowlisted ref, `make dist` in the pinned Go image and the MSI steps in the msitools image (unprivileged, read-only, caps dropped, CPU/memory limits, 25 minute deadline, status heartbeats), self-verification (PE header and machine, version string, MSI file type, the agent's own `version` output), `SHA256SUMS`, chunked upload (at most 1 MiB, per-chunk SHA-256, retries with backoff), `complete` with the manifest, cleanup on every exit path, lock file, https only (`BUILD_HOST_ALLOW_HTTP=1` for tests), token kept out of logs and the command line. Modes `--once`, `--register` (announces no capabilities so it never claims a job), `--dry-run` (no server contact).
- Tests: `endpoint-agent/e2e/mock_build_host_server.py` (strict mock of the four endpoints) and `e2e/test_build_host.py` (13 tests, no Docker build; new CI job `build-host` also runs shellcheck). `e2e/run_build_host_proof.sh` (manual): real Docker build of the committed HEAD against the mock, 35 checks, 0 failed on one host (Linux x86-64): exe and arm64 exe byte-identical to a direct `make dist`, MSI byte-identical between two independent builds, 9-chunk uploads surviving injected 503s, refusals (non-allowlisted ref, missing ref, http), docker killed mid-build reported as failed with no leftovers, lock behaviour.
- Build progress: the `status` call gained optional, backward compatible fields `stage` (prepare, clone, build_windows_amd64, build_windows_arm64, msi, verify, upload), `pct` (0-100, never decreases, 100 on the last status before `complete`), `detail` (at most 120 printable characters) and `elapsed_s`. `build-host.sh` sends them at every stage start and finish, every 15 s during long steps (this replaces the old 120 s lease heartbeat; between heartbeats the percentage creeps toward the end of the stage) and after every uploaded chunk; calls are retried quietly (3 tries, short timeout) and a failure never fails the build. New `--progress` flag (default on when stderr is a terminal) prints `progress: stage pct% elapsed detail` lines. The mock server validates and records the fields (stage allowlist, integer range, printable detail, no decreasing pct or stage); new unit test; the real-Docker proof asserts the seven stages in order, non-decreasing pct from 0 to 100, and the operator lines. Approximations: the amd64/arm64 split inside one `make dist` is inferred from the amd64 file appearing; no heartbeat during the short `clone` step. Protocol and operator docs updated.
- Notes: `make msi` cannot run inside the Go container (it starts Docker), so the script runs the same MSI commands on the host. Not proven: the server side, TLS (tests use http via the override), a real GitHub-hosted comparison, non-x86 hosts. The protocol did not define `--register` or the `log_tail` field name; this script uses `log_tail` on `failed` and a no-capability poll.

## 1.0.0-rc.25 (RMM: the agent reports the basic metrics on every check-in)

Found on a real Windows device: only CPU, memory and disk utilization and network rate arrived on every check-in, so the asset Metrics charts for memory bytes, disk bytes, per-core load, disk I/O, network errors and battery stayed blank. Additive to the frozen device protocol (PROTOCOL.md 3.2.9): new OPTIONAL `metrics` members; old agents and old servers keep working.

- **Agent.** `mem_used_bytes`, `mem_available_bytes`, `mem_total_bytes`, `disk[].free_bytes/total_bytes`, `uptime_s`, `pending_reboot` (0/1), `cpu_core_pct` (cap 256), `disk_read_iops`, `disk_write_iops`, `disk_queue`, `net_errors`, `battery_pct`, `battery_charging`, each left out when its collector fails. Linux: `/proc/stat`, `/proc/diskstats`, `/proc/net/dev`, `/sys/class/power_supply`. Windows: `NtQuerySystemInformation` (per core), `IOCTL_DISK_PERFORMANCE` (IOPS, queue), `GetIfEntry2Ex` (errors), `GetSystemPowerStatus` (battery); no PDH or WMI. The Windows code cross-compiles and vets but was NOT run on Windows. Optional `ExtraPlatform` interface, so other platforms and fakes are unaffected.
- **Server.** `CheckinService` maps them to the existing keys (`memory.used_bytes` ... `battery.charge_percent`, per-core instances `0`..`255`, per-mount disk bytes), each value validated on its own. New limit `metrics_extended` (0/1, default 1) switches the group off. `DatabaseMetricSink::ROLLUP_KEYS` gains eight keys. `last_metrics_json` keeps its five members. Capacity numbers: CAPACITY.md 6.1.
- Not collected: `gpu.*`, `battery.health_percent`, `cpu` temperature; `battery_charging` is accepted but has no metric key.
- Tests: Go unit tests with fake collectors (`metrics_ext_test.go`, `linuxextra_test.go`, a vector round trip), PHP integration tests in `CheckinTest` (every key, switch, hostile input, old-style check-in, buffered batches, shared vector `tests/Fixtures/rmm/vectors/metrics-extended.json`).

## 1.0.0-rc.23 (RMM device clock skew: wider window, self-correcting agent, visible reason; migration 0031)

Found on a real PC whose clock was five minutes ahead: every check-in was refused ("collected_at is in the future") and the console only said the OS and agent had not reported. All of it is additive to the frozen device protocol; old agents and old servers keep working. See [docs/rmm/CLOCK_AND_TIME.md](docs/rmm/CLOCK_AND_TIME.md) and PROTOCOL.md 3.2.8.

- **Window.** `RmmProtocol::CHECKIN_FUTURE_SKEW_S` 300 to 900 (new constant `CLOCK_OFFSET_MAX_S` 86400); the same window for buffered samples, job report times and log and change record times.
- **Refusal.** The 422 for a time outside the window carries `server_time` and `skew_s` (`ApiError::badTime()`, `ApiError::$extra`).
- **Agent.** Clock offset estimate from `server_time` (and the `Date` header), smoothed, persisted, capped at 24 h, applied above 60 s to every stamp (samples, buffered, job reports, log events, change records); one warning per hour; one immediate corrected retry after a time refusal; optional `clock_offset_s` in the check-in.
- **Server.** Migration `0031_rmm_clock_skew`: six nullable columns on `endpoint_agent_devices` (`clock_skew_s`, `clock_skew_at`, `clock_offset_s`, `clock_skew_event_at`, `last_reject_reason`, `last_reject_at`), written inside the check-in's existing UPDATE (no extra statement on the hot path). Device detail gains `clock` (`RmmReadModel::clockOf()`); the live document only when worth showing. New event `rmm.device.clock_skew` (35 `rmm.*` events), once per device per day above the new `clock_skew_alert_s` limit (default 120, 0 = off).
- **Golden transcripts.** One exchange (`collected-at-in-the-future`) differs by the two additive members, declared as `CLOCK-SKEW` in `expected-deltas.json`; the replay adapter leaves the new device columns out of its snapshots.

## 1.0.0-rc.22 (RMM change monitoring: registry, files, groups, tasks, Security log presets; migration 0030)

Built in Core, **not adopted by an edition yet**, behind the `change_monitor` sub-switch (off, with a storage acknowledgement). Know what changed on a machine, when and (on Windows, when recorded) who did it, in the same database, with retention and caps like the log feature: [docs/rmm/CHANGE_MONITOR.md](docs/rmm/CHANGE_MONITOR.md) has the model, the privacy rules, the scale numbers (a measured 470 bytes per record), the security review and what is proven. Built after Phase 5 (rc.21) on the same pattern: capability negotiation, a signed configuration, abilities, a conformance kit with mutants.

- **Agent.** New package `internal/change`. Announces `change:monitor` (and `logs:presets`); `disable_change` in `config.json` withdraws the first and wipes what was kept; `change_extra_roots` lets a local administrator add file roots. It verifies the signed `config.change` against the pinned key BEFORE reading anything, applies its own copy of the watch policy and clamps every number, keeps a redacted snapshot per watch in `change_state.json` (0600), reports only the difference (the first reading is a silent baseline; a changed watch specification re-baselines; an unreadable key is not a removed key) and ships through a persisted queue with a per-minute budget and back-off. Watches: Windows registry values (HKLM and every loaded user's HKU; secret-named values are never read, hashed with a device-local key), the local Administrators group (`net localgroup`, a localised Windows resolved by SID), scheduled task definitions, files and folders on both platforms (hash, the lines added and removed with secrets redacted before they are stored, permission and owner changes, symlinks never followed). Windows also polls sooner on `RegNotifyChangeKeyValue` and asks the Security log for event 4657 to fill the actor (blank when not audited). **The Windows registry, group, task, notification and actor code has never run on a Windows host**; it is cross-compiled, vetted and unit-tested with fakes and fixtures.
- **Security log presets.** `logs_collect.presets` (eight named presets: account changes, group membership, repeated failed logons, log cleared, scheduled task, new service, audit policy, new device) expand into three ordinary `eventlog` sources. Audit events have Level 0, so these sources read every level (`levels: []`); failed logons (4625) are **aggregated on the device** (`aggregate: {window_s, min, by}`) and the aggregated source is offered only to an agent that announced `logs:presets`. `Logs\SecurityLogPresets`, `RemoteSettings::logPresets()`, agent `internal/logs/aggregate.go`; the agent reads up to 24 sources (was 16).
- **Migration `0030_rmm_change_monitor`** (idempotent, no row inserted): `endpoint_agent_change_settings`, `endpoint_agent_change_records`, `endpoint_agent_change_state`, `endpoint_agent_change_rules`.
- **Server.** `Change\ChangeSettings` (presets, custom watches, caps; builds the signed configuration: Ed25519 over a domain line, a line feed and the canonical JSON; never offered unsigned), `ChangePresets`, `ChangeWatchPolicy`, `ChangeService` (bounded ingest: per-minute budget, device and fleet caps, duplicates stored once, every record checked against the watches that device was given and against the policy, texts cleaned and redacted again; search, a "who changed what" timeline that merges the software inventory, retention in batches), `ChangeRuleService` (alerts through the check evaluator, a recommended set), `ChangeActions`, `Http\ChangeApi`, `DeviceApi::changes()`.
- **New device endpoint `agent_changes`** (POST, device token): an edition must route it like `agent_logs` (UPGRADING.md). Additive: an agent that does not announce `change:monitor` is answered exactly as before and the golden transcripts replay identically. `docs/rmm/templates/rmm_gate.php` answers the new name too.
- **Abilities.** `rmm.change.view` (map like `rmm.job.run_saved`), `rmm.change.manage` (presets, custom watches, rules; needs all-client access for the global parts). The switch and the caps need `rmm.admin`.
- **Routes** (additive, [openapi-device.yaml](docs/rmm/openapi-device.yaml)): `endpoint_devices/changes[/stats|/settings|/rules[/{id}|/recommended]]`, `endpoint_devices/{id}/changes[/timeline|/status]`. A device or client outside the caller's clients is the same 404 as a missing one on every route (tested per route with a client-restricted user).
- **New optional contract.** `Rmm\Contracts\ChangeWatchPolicyInterface` with `RivetCore\Testing\ChangeWatchPolicyConformanceTestCase`, proven by 37 deliberately broken policies in `KitMutationTest` (SAM or SECURITY in one spelling only, the long hive name, a whole hive, HKCU, collapsed backslashes, trimmed input, the LSA boot-key parts, ControlSet001, shadow files, SSH host keys, `ssl/private`, user keys, VPN and Wi-Fi secrets, secret file names, a prefix test a `..` walks around, relative paths, whole system folders, trailing and doubled separators, Windows hive files and traversal, forward slashes, drive roots, stripped control characters, an unknown kind, throws on garbage, full-width and zero-width lookalikes, flip-flopping answers, a client id that loosens the rules, a non-bool answer). The kit found two real gaps in Core's own default policy while it was written (trailing space, zero-width space), fixed.
- **Shared vectors.** `endpoint-agent/testdata/vectors/agent_change_monitor_vectors.json`: the policy's answer for 127 keys and paths (PHP decides, Go must agree), the secret-name rule and one complete signed configuration (PHP signs, Go verifies; one changed character breaks it; a job-style signature does not verify as a configuration); `SHA256SUMS` and `PROTOCOL.md` (3.2.7, 3.9) updated; the four older vector files keep their bytes.
- **Events.** `rmm.change.detected` (at most 20 per batch), `rmm.change.rule_matched` (34 `rmm.*` events).
- **Limits.** `change_retention_days` (90), `change_device_max_rows` (5,000), `change_fleet_max_rows` (500,000), `change_rate_per_min` (120), `change_interval_s` (300), `change_max_value_bytes` (256) in the change settings row; `CapacityReport::build()` gains a `change_monitor` block; [CAPACITY.md](docs/rmm/CAPACITY.md) section 21.
- **Found by the tests and the proof.** The default poll interval (300 s) is longer than the first proof run waited; the XML decoder looped forever on a task file whose declaration says UTF-16 (the text was already decoded; fixed with a test); the first design wiped the snapshots as soon as the offer disappeared, which would have lost every change made while a server under load withdrew it (now kept for a day, wiped at once by the local switch or an explicit `feature_disabled`); a failed back-off was shortened to the polling interval and a pause the server asked for was not waited in full.
- **Honest status.** Proven: PHP `ChangeMonitorTest` (21 tests, about 500 assertions: signed configuration, rogue device, caps, retention, scope, timeline, rules, events, settings, custom watches, Security presets, statement counts), `ChangeWatchPolicyKitTest` (12) with 37 mutants, `SchemaDiffTest`-style migration checks, the vectors; Go `internal/change` (about 60 tests), `internal/logs` aggregation, agent capability and end-to-end tests; `GOOS=windows go vet ./...`; and `endpoint-agent/e2e/run_change_proof.sh` (`CHANGE PROOF PASS`, CHANGE_MONITOR.md section 13): the real Linux agent under real systemd against the real PHP server through TLS. **Not run: any Windows path.** Environment note: `StorageScaleTest::testWithoutThePrivilegesTheProbeSaysSoAndNothingIsChanged` needs a MySQL account that may `CREATE USER`; it errors with a restricted scratch account and is unrelated to this change. `TestShellJobProcessGroupKilledOnTimeout` fails inside the build container (also on the base commit); it needs an init process.
- **Editions.** See UPGRADING.md ("Adopting change monitoring"): migration 0030, two abilities, **route `agent_changes`**, the pages, an agent rollout.

## 1.0.0-rc.20 (RMM Phase 4: patch management; migration 0028, agent 0.8.0)

Phase 4 ([#72](https://github.com/TheTractorHacker/rivet-core/issues/72)), built in Core, **not adopted by an edition yet**, behind the `patching` sub-switch (off). Detect first, install gated: [docs/rmm/PATCHING.md](docs/rmm/PATCHING.md) has the model, the safety defaults and what is not done.

## Crypto: envelope, settings vault, rewrap, vault key wrapping (unreleased)
Items 19 and 20 of the [platform gap analysis](docs/program/PLATFORM_GAP_ANALYSIS_2026-10.md): the shared encryption implementation both editions use. New namespace `RivetCore\Crypto`, all additive, **built in Core only**: no edition has adopted it, nothing changes for an install until it does. No migration (0021 stays free). Decision record: [ADR-011](docs/architecture/ADR-011-envelope-and-key-standard.md); guide with runnable examples: [docs/modules/crypto.md](docs/modules/crypto.md); adoption steps for editions: [UPGRADING.md](UPGRADING.md) "Adopting Crypto".

- **Envelope.** `v3:<kid>:base64(nonce12 || tag16 || ciphertext)`, AES-256-GCM through ext-openssl (**new requirement `ext-openssl`**), the caller's context string (record type and id) as AAD. `Envelope` / `EnvelopeInterface`: `seal`, `open`, `needsRewrap`, `rewrap` (verifies the result), `label`. Typed failures `DecryptionFailed`, `UnknownKeyId`, `KeyUnavailable`, `InvalidKeyMaterial` (all `CryptoException`); never partial plaintext, never `''` for a failure, sealing without a key fails closed. Non-canonical base64 is refused.
- **Keys.** `KeyRing` (kid to 32 bytes, one active, others decrypt-only; weak and duplicate keys refused), `KeyGenerator` (`random_bytes`, `rotate()`, `fingerprint()` with the editions' `rivetit-settings-key-fingerprint|v1|` formula, `ringFromLegacySettingsKey()`), `KeyPurpose` (HKDF-SHA256 labels `settings`, `totp`, `media-token`, `training-pin`, `vault-wrap`, `signing-seal`), `KeyFile` / `KeyRingLoader` / `KeyRingLoadResult` (JSON or PHP array file outside the web root, environment fallback, refuses a world-writable file, warns on world-readable, group-writable, foreign owner and inside-the-web-root, `strict` mode, atomic 0640 write that refuses to overwrite).
- **SettingsVault.** Named secrets bound to their name, per-purpose subkeys from one master KEK, fail-closed, lazy re-wrap (`read()` returns the replacement ciphertext; `decrypt()` hands it to a callback and a failing callback never fails the read), `subkey()` for HMAC keys.
- **Legacy readers.** `LegacySettingsGcmReader` (`ENC2:`), `LegacySettingsCbcReader` (`ENC:`), `LegacyOtpReader` (`enc:` TOTP seeds), `LegacyUserKeyReader` (`V2:`, optionally V1), `LegacyVaultFieldReader` (old credential fields), opt-in `PlaintextPassthroughReader`, factory `LegacyReaders`. They throw where the editions returned `''`. Tested against samples written by the editions' own function bodies (`tests/Fixtures/crypto/`).
- **Rotation and rewrap.** `RotationPlan` (pure), `Rewrapper` with `RewrapSource`, `RewrapItem`, `Reencryptor`, `EnvelopeReencryptor`, `RewrapOptions`, `RewrapReport`, `RewrapState`, `RewrapStateStore`, `FileRewrapStateStore`: resumable, idempotent, compare-and-set writes, dry run, failure and conflict counting, one `crypto.rewrap` audit event per run when an `AuditService` is passed.
- **Vault primitives.** `VaultKeyWrap` (DEK wrap `vw3:<kdf>:<params>:<salt>:<payload>`: Argon2id, else PBKDF2-SHA256 600000+, parameters stored and authenticated, password change = `rewrap()`, instance-KEK wrap for recovery, `openLegacyUserKey()`), `KdfParams`, `VaultCipher` (credential fields in v3 with AAD `credential:<id>[:<field>]`, `migrate()` from a legacy field), `VaultFieldReencryptor` (legacy to v3 and DEK rotation through the `Rewrapper`).
- **Conformance kit.** `Testing\EnvelopeConformanceTestCase` and `Testing\RewrapSourceConformanceTestCase` with `InMemoryRewrapSource` and `InMemoryRewrapStateStore`; 12 envelope and 11 source mutants in `KitMutationTest`.
- **Tests and docs.** About 180 new tests (119 unit, 38 kit cases, 23 mutant checks): known-answer vectors from an independent library, NIST/McGrew-Viega GCM test case 16, KDF vectors, tamper/truncation/bit-flip fuzzing, nonce uniqueness, legacy round trips, rewrap resumability and crash recovery, and every example in `docs/modules/crypto.md` is executed. `scripts/bench.php --crypto` (no database needed) and a section in `docs/PERFORMANCE.md`.
