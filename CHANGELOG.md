## 1.0.0-rc.45 (reporting views and Power BI guide, phases 1 and 2 of #91; migration 0047)

Phases 1 and 2 of [#91](https://github.com/TheTractorHacker/rivet-core/issues/91): stable, safe SQL views for Power BI and any BI tool, a read-only account for them, and the documents and samples to use them. **Additive: nothing changes for an edition that does nothing.** No table, column or row is touched (the migration only creates views), no public signature or constant changed, the device protocol and the golden replay are untouched. Design: [docs/design/reporting.md](docs/design/reporting.md). Guide: [docs/reporting/POWER_BI.md](docs/reporting/POWER_BI.md).

- **Migration 0047** `0047_reporting_views`: 17 `rpt_` views in the control database (`CREATE OR REPLACE VIEW`, idempotent; needs `CREATE VIEW`; owned by the account that runs it). **PostgreSQL migration `0002_reporting_views`** (in `PostgresMigrator`'s default list, so `rmm-postgres.php migrate` applies it): the six views over the hot tables in the PostgreSQL store.
- **The views** (`ReportingCatalog`): `rpt_devices` (state, status, headline patch state), `rpt_device_groups`, `rpt_device_tags`, `rpt_device_health_hourly` / `_daily` (metric roll-ups), `rpt_alerts` (open and history with duration and time to acknowledge), `rpt_check_status`, `rpt_check_results` (last 31 days), `rpt_patch_compliance`, `rpt_patch_updates`, `rpt_patch_history`, `rpt_software_inventory`, `rpt_software_changes`, `rpt_hypervisor_hosts`, `rpt_hypervisor_vms`, `rpt_change_events` (counts and types only), `rpt_audit_events` (summary only). Allow-list of columns (never `SELECT *`, an explicit column list per view), UTC, `client_id` on every client-scoped row (joined from the device where the table has none; a metric view resolves an asset to its newest device so a re-enrolled asset is never counted twice). Tickets, SLA, client / site / asset names are the editions' tables: the proposed edition views are in the design note (section 7), the prompts in [docs/design/reporting-edition-prompts.md](docs/design/reporting-edition-prompts.md).
- **Frozen contract.** `tests/Fixtures/reporting_views.json` pins every view's column names, order and logical types; a column can only be added on purpose (the test says how). A deny-list test scans every exposed column name and every base column the SQL reads for token, secret, password, hash, key, credential, cookie, signature, `_enc` and friends, and free-text or personal-data parts (output, script, command, detail, message, summary, ip, mac, serial, json); a second test plants a marker in every excluded column and proves it never appears in any row of any view.
- **`ReportingRole`**: returns (never executes) the SQL for a read-only reporting account: MariaDB / MySQL (`REQUIRE SSL`, `MAX_USER_CONNECTIONS`, `SELECT` on the views only, `REVOKE ALL` first so a re-run rotates the password and removes grants added by hand) and PostgreSQL (`NOSUPERUSER`, connection limit, read-only default transaction, statement timeout, UTC, `SELECT` on the views only), plus drop statements and TLS notes. `generatePassword()` returns a random password for the caller; nothing stores it. Every identifier and the password are validated against strict patterns before they reach SQL.
- **Documents and samples** in `docs/reporting/`: the Power BI guide (connectors, Import versus DirectQuery, query folding, incremental refresh, the gateway and scheduled refresh, TLS and network exposure, least privilege, per-client row-level security with DAX, performance, time zones, troubleshooting), the data dictionary and entity diagram (generated from the catalog), a Power Query (M) file for every view and both sources, DAX measures (device availability %, patch compliance %, mean time to resolve, alerts per 100 devices, top noisy checks, storage growth per day, active devices in the last 7 days, ...), edition-dependent measures (tickets per 100 devices, SLA breach rate), and a step-by-step starter report. `php scripts/reporting-docs.php` regenerates the generated parts; a test fails when they are stale. **Not verified in Power BI Desktop** (none available): the M and DAX text is structure-checked and the SQL behind it runs against real databases.
- **Known limit (decision for Blake).** The PostgreSQL metric, check-history and software-history tables carry no `client_id` and the store has no device table, so those four PostgreSQL views have `asset_id` or `device_id` only and are scoped by client in the model through `rpt_devices` (documented). Denormalising `client_id` into them is the recommended follow-up (design note 3.2).
- **Tests added (107).** Unit: the view contract and freeze, the no-secrets scan, the role SQL and its injection refusals, the generated-docs freshness check and the Power Query / DAX structure checks (55). MariaDB / MySQL: columns and type families of every view, idempotent migration, a tenant test per client-scoped view (a query for one client returns exactly that client's rows), the planted-marker secrets test, status / alert-duration / patch / dedupe / time-bound cases, the SQL behind every sample, the read-only account (it reads the views, it cannot read a base table or write or run DDL, rotation, exact grants, TLS requirement) and an EXPLAIN-and-timing test on about 600,000 synthetic rows (32). PostgreSQL: the same for the six hot views, the role, and plans and timings on about 640,000 rows (20). The migration list tests were updated for 0045 and for the PostgreSQL migration `0002_reporting_views`.
- **Verification (all executed in throwaway Docker containers with random passwords; nothing live).** `composer lint`, PHPStan level 6 (no errors), the two CI shell rules (no `mysqli` or request globals in `src`, PDO only under `Store/Postgres/Pdo`), `php scripts/api-surface.php` regenerated after a real `composer install`, Roave backward-compatibility check against `v1.0.0-rc.42` (only the 203 known `PHPUnit\Framework\TestCase could not be found` skips, no real break). The full suite on MariaDB 10.11 with PostgreSQL 18 and Redis 7: 3,857 tests, 137,324 assertions, no failures (63 skipped: Docker-in-Docker, TimescaleDB and environment skips; 1 warning: the PowerShell parser test cannot start Docker from inside the test container). The new reporting tests also on MySQL 8.4 and on TimescaleDB 2.31 (PostgreSQL 18). Timings on the synthetic data, filtered by date and device, asset or client: 1 to 8 ms on MariaDB (the whole fleet for the last 2 hours: 200 ms), 1 to 62 ms on PostgreSQL, every query using an index of the big table.

- **`Backup\BackupFactsProviderInterface`** (`@api`) plus `BackupFacts`, `BackupStore`, `RestoreTestFact`, `UnavailableBackupFactsProvider` and `Testing\BackupFactsProviderConformanceTestCase` (never throws, repeatable, no future timestamps, nothing claimed without a successful backup, an off-site arrival needs an off-site destination, no secrets), with seven mutation tests in `KitMutationTest`. The edition reports what its backup did; Core never reads edition internals.

## 1.0.0-rc.43 (RMM data store info for update pages; no migration)

Additive. No migration, no schema change, no changed signature or constant value. An edition that does nothing behaves exactly as before; the golden replay and the device protocol are unchanged.

- **`DataStoreInfo` (new, `RmmModule::dataStoreInfo()`)**: `report(bool $probe = false, bool $tables = false): array` tells an Update or Server page which RMM data store is in use and, for PostgreSQL, whether it is reachable (a live check, 2 s connect and statement timeouts, behind the data store's own circuit breaker), the server version (`18.6` plus the full string and parsed major/minor), the storage mode (`native`/`timescale`) and TimescaleDB version, the schema state (`applied`, `pending`, `changed`, `current`, `up_to_date`), host/port/database (never the role, a password, the sealed value or a DSN) and `pg_database_size`; with `$tables` also the rows and bytes of the hot tables (the phase 3 `PostgresStoreSizes` report). It never throws. On a MariaDB install it makes no PostgreSQL connection and no PostgreSQL query unless `$probe` is true; it then reports the saved connection (`configured`, `saved`) so a page can say "PostgreSQL configured but not in use". With a shared cache (`cache` module option) the live answer is kept 30 seconds. `error` is one of a fixed set of short sentences, never the driver's text (a server message can name the role).
- **`DataStoreInfo::summaryLine(array $info): string`**: pure helper for a tile, for example `PostgreSQL 18.6 (native) - schema 0001_hot_tables, up to date`, `PostgreSQL unreachable: connection refused`, `MariaDB (PostgreSQL not in use)`.
- **Docs**: docs/rmm/POSTGRES.md section 18 "Showing the data store on an Update page" with ready-to-paste snippets for `update.php` and the server status page; UPGRADING entry (nothing required).
- **Tests**: `tests/Integration/Rmm/DataStoreInfoTest.php` (MariaDB control database, fake connector: no PostgreSQL on a MariaDB install, no secret in any result, every failure an answer, cache honoured, summary line variants) and `tests/Integration/Rmm/Postgres/DataStoreInfoPostgresTest.php` (real PostgreSQL in a role and database created per test with random names: version, schema, mode, size, pending and changed migrations, empty database, wrong password, refused port and blackhole address answered in under 5 s, cache).

## 1.0.0-rc.41 (RMM data store: setting, migration command, capacity recommendation, backup helpers; migration 0044)

Phase 3 of [#89](https://github.com/TheTractorHacker/rivet-core/issues/89). Additive for everything that does not opt in: an install on MariaDB behaves as before, loads no PostgreSQL code and opens no PostgreSQL connection; the golden replay and the device protocol are unchanged. Editions: see UPGRADING.md "Adopting the data store setting and migration" and docs/design/rmm-data-store-phase4-edition-prompts.md.

- **Migration 0044** `0044_rmm_store_switch`: nullable `endpoint_agent_settings.data_store_phase` (`copy:<store>` / `dual:<store>` while a migration runs; read with the settings row, no extra query), tables `rmm_data_store_connection` (one row; password sealed) and `rmm_store_migration` (one row per run). Additive and idempotent; code before migration is safe.
- **`DataStoreSwitch`** (`RmmModule::dataStoreSwitch()`): the one supported way to choose PostgreSQL (`RmmSettings::update()` still refuses it). `saveConnection()` stores host, port, database, role, sslmode, schema and the password **sealed with the SecretBox** in its own table; `testConnection()` checks the extension, the connection, version 14 or newer, UTC, the schema, that the role can create objects (a rolled-back `CREATE TABLE`), warns about a superuser role, detects TimescaleDB; `switchTo('postgres')` tests, runs the PostgreSQL migrator, then writes connection and setting in one transaction or changes nothing; `switchTo('mariadb')` is always allowed; `status()` for the card. **Switching does not move rows and the old history is not shown** (a read-through that merges two stores was judged riskier and rejected, docs/design/rmm-data-store.md 13.1); `status()['left_behind']` names what stayed behind and `NO_DATA_MOVE_NOTICE` is the text the card must show. The module uses the stored connection when the edition passes no `postgres` option.
- **Security (found by review before release).** The stored sealed password is reused for a blank password field **only for the same host, port, user and database**; changing any of them makes `saveConnection()`, `testConnection()` and `switchTo()` refuse ("Enter the password again ...") before the password is decrypted or any connection is attempted, and a remote host needs `sslmode` `verify-full` or `verify-ca` to reuse it. Without this a hijacked administrator session could have pointed the host at another machine and made the "Test connection" button send the stored password to it. The connection cannot be edited while a migration runs. The migration, the size report and the scripts read the target from the stored settings only. The password is never logged, audited, returned, in a JSON progress line or an exception message.
- **`RmmStoreMigrator` and `scripts/rmm-store-migrate.php`**: `--from/--to` both ways, `--dry-run`, `--batch`, `--pause-ms` (and a back-off while the load shedder is active), `--sample`, `--resume`, `--rollback`, `--purge-old --yes`, `--abort`, `--status`; JSON lines and a final summary. Keyset pages (never `OFFSET`) with surrogate ids kept and a no-op conflict clause, a checkpoint per batch, **retention and rollups paused** until the cut-over, a **dual-write window** (`Store\Migration\DualWrite`: primary first, secondary after; a secondary failure is counted and blocks the cut-over), a tail pass that reconciles the rows around the dual-write start as multisets, ledgers (`log_state`, `change_state`) rebuilt from the copied rows, verification (row counts over a stable range, ledger against rows, checksum of a sample of devices or all), one repair attempt, then the cut-over in one control transaction. The old store is kept untouched for `rmm_store_rollback_days` (default 7); `--rollback` copies back what the new store received since the cut-over and flips; `--purge-old` is the only deletion and is never automatic. Audit rows for start, cut-over, rollback, purge, abort. Details and the named limits of the method: design note 13.4 and 13.5.
- **Capacity recommendation**: `CapacityReport` gains `store_sizes` (rows and bytes of the hot tables of the ACTIVE store: MariaDB `information_schema`, PostgreSQL `pg_total_relation_size`/`reltuples`, TimescaleDB `hypertable_size`; an unreachable store answers `available = false`) and `data_store_recommendation` (`Capacity\DataStoreRecommendation`: devices N, `rmm_pg_recommend_devices` X default 5000, hot size and `rmm_pg_recommend_hot_mb` default 51200, growth per day; the message "MariaDB is comfortable up to X devices. ## 1.0.0-rc.40 (RMM data store: Postgres implementation, phase 2 of #89; migration 0043)

Additive for everything that does not opt in: an install on MariaDB behaves as before, never loads the PostgreSQL code and never opens a PostgreSQL connection. The RMM device protocol is frozen and untouched (the golden replay is identical); the only new device-visible behaviour is the existing retryable `503 unavailable` for a log or change batch while a PostgreSQL store is down. Design: [docs/design/rmm-data-store.md](docs/design/rmm-data-store.md) section 12. Operator guide: [docs/rmm/POSTGRES.md](docs/rmm/POSTGRES.md).

- **PostgreSQL stores** for all twelve hot tables: `Store\Postgres\Postgres{Metric,CheckHistory,Log,ChangeEvent,SoftwareHistory,PatchHistory,DeploymentHistory,HypervisorHistory}Store` and `PostgresStoreMaintenance`, with every MySQL idiom of the design note translated (`ON CONFLICT`, `bytea`/`decode`, `ILIKE ... ESCAPE`, joined sub-select deletes, advisory locks, `to_char(... AT TIME ZONE 'UTC')`). Per-device counters keep their same-transaction semantics. `@internal`.
- **Connection port.** `PostgresConnectionInterface` (query, queryOne, value, execute, transaction with savepoints and deadlock retry, UTC session, statement/lock/idle timeouts, server-side prepared statements), `PostgresConfig` (validated, password hidden from dumps and traces, `fromSealed()` with the existing `SecretBoxInterface`), `Pdo\PdoPostgresConnection` (the only class that mentions PDO; a CI rule enforces it), `CircuitBreakerConnection` (one connect timeout per worker per window during an outage; state shared through a small file), the `PostgresException` family mapped from SQLSTATE (connection, serialization, timeout, query; no DETAIL line, bound value or password in a message). `@api`.
- **Schema and migrator.** `PostgresSchema` (bigint ids, `timestamptz`, `jsonb`, `bytea`; B-tree and BRIN chosen per access pattern; the three big time series are range-partitioned with a DEFAULT partition, or TimescaleDB hypertables), `PostgresMigrator` with its own ledger `rivet_core_pg_migrations` (idempotent, versioned, advisory-locked, one migration per transaction), `scripts/rmm-postgres.php migrate|status`. TimescaleDB is detected with `SELECT extname FROM pg_extension`, never required and never created; continuous aggregates are deliberately not used (design note 12.4).
- **Partitions and retention on PostgreSQL.** Day partitions created ahead (rows moved out of the DEFAULT partition atomically under a short lock), expired partitions dropped whole, never before the daily rollup covered them; or, on TimescaleDB, compression after 7 days and `drop_chunks` with the same guard. Same `partitioning` limits as MariaDB.

- **Degraded behaviour.** Check-in and job-result history writes never throw: dropped and counted in the new control table `rmm_hot_store_faults` (`HotStoreFaults`, one `error_log` line a minute, the `data_store` block and warning in the capacity panel, `RmmModule::dataStoreHealth()`, `clearDataStoreFaults()`); log and change batches get a retryable 503; reads throw `HotStoreUnavailableException` (the metric readers answer "no data"); housekeeping reports nothing done. No connection configured behaves the same, with the precise reason. See design note 12.7.
- **Blake's decisions on phase 1.** (1) A store never joins `endpoint_agent_devices`: `client_id` is stored with every log entry and change record (and in the change ledger), `admit()` takes it, search/timeline rows carry `device_id` and `client_id` and no host name, `Store\DeviceNames` adds host names in `LogService::search()`, `ChangeService::search()` and `timeline()`; the package name moved to `DeployReader::history()`; `deleteOrphans()` takes a closure that says which VMs exist. (2) `rmm_package_history` and `rmm_hypervisor_vm_history` stay HOT. (3) The rollup watermark lives in `rmm_metric_rollup_state` next to the tiers (MariaDB: new table, old row still written so a rollback loses nothing; PostgreSQL: its own table). (4) Migration 0042 unchanged.
- **Behaviour changes on MariaDB worth knowing.** Search rows of a deleted device stay visible in unscoped searches until retention (with an empty host name); a row without a client (written during the upgrade window) is invisible to a client-scoped reader; tie-breaks were added to three `ORDER BY ... LIMIT` queries so equal counts list in a fixed order. `SoftwareHistoryStore::sharesControlTransaction()` keeps the history inside the inventory transaction on MariaDB (as before) and after the commit on a store in another database. Log/change rule evaluation that cannot read the store no longer fails an already stored batch.

Additive, idempotent. Run it with the code; if the code arrives first, nothing breaks: the MariaDB log and change stores notice (once per process, from the server's "Unknown column" answer, with no extra query when the column exists) that `client_id` is missing and run the pre-rc.40 statements instead, scoping searches by a sub-select of the device table until the migration runs (`Store\\MariaDb\\ClientColumn`).

- **Performance and write path.** A check-in's metric write is one statement on PostgreSQL (a data-modifying CTE: latest readings and hourly rollups, one round trip). The PDO adapter keeps 64 prepared statements per session. History writes of a check-in wait for the control database transaction to commit (`Guard\\WriteBehind`, fed by `Support\\TrackedDatabase`, wrapped around the control database by the module) and are dropped if it rolls back, so PostgreSQL latency or a connect timeout is never spent inside the device-row lock. `scripts/rmm-store-bench.php` compares the two stores; numbers (one noisy host, fsync-bound) are in design note 12.10: with the commit flush relaxed on both, PostgreSQL ingests 600 check-ins per second against MariaDB's 212.

## 1.0.0-rc.14 (fix: asset page thresholds failed on a check with empty params)

Bug fix. Loading the Alerting thresholds part of an agent-linked device logged `Cannot use object of type stdClass as array` from `AlertingActions::getThresholds` and the part failed.

- **Root cause.** Inside the module a check definition's `params` was sometimes a `\stdClass` instead of an array: `RmmSettings::defaultChecks()` built `pending_reboot` with `new \stdClass()` and `settings->checks()` returns that list whenever no `checks_json` is stored (every install that never edited its checks), `ChecksValidator::validate()` returned `stdClass` for empty params, and `EffectiveConfig::compose()` (the per-device policy list) converted empty params to `stdClass` too. Anything that read `$def['params']['thresholds']` (`getThresholds`, `setThresholds`) then threw; `AlertingEngine::definitionsOf` only survived through an `is_array` guard. Present since the thresholds routes first shipped (rc.10); invisible in tests because they always stored a list through `json_encode` and read it back as arrays.
- **Fix.** Inside the module `params` is always an array. `\stdClass` now exists only at the wire edges: `ChecksValidator::toWire()` turns an empty `params` into `{}` for storage (`checks_json` still stores `{}`), for the settings read model, the policy explanation, the policy version hash and (as before) `signCheckList()` / `Signer::checkMessage()`. `ChecksValidator::paramsOf()` reads a definition's params as an array whatever shape it arrived in, and `AlertingActions` uses it, so a hand-built definition with `stdClass` params also works. Wire bytes are unchanged: the golden transcripts still replay identically (`replay identical (10 files)`), the signed check messages and the policy `version` hashes are byte for byte what they were.
- **Audit.** Every `json_decode(` in `src/Rmm` was checked: all decode as arrays except the three that need objects on purpose (`Signer::checkMessage` and `JobService::jobObject`, which keep `{}` vs `[]` for the signed bytes, and `InstallerStamp`, which only tests `is_object`). The other `\stdClass` producers (`JobService`, `ScheduleService`, `ScriptActions`, `PolicyStore`, `RmmSettings` features/limits, `StarterPack`, `StarterInstaller`) only build output or hashes and never read the value back as an array.
- **API (additive).** `ChecksValidator::toWire()` and `ChecksValidator::paramsOf()`.
- **Tests.** `CheckParamsShapeTest` (the default list and the four checks of the real agent, `{}` and `[]`, the technician `device/{id}/alerting` and `checks/{key}/thresholds` GET/PUT/DELETE routes, a Phase 3 check with thresholds, a policy-provided template, no `stdClass` in any internal list); `ChecksValidatorTest` and `EffectiveConfigTest` now assert arrays inside and `{}` on the wire.

## Crypto: envelope, settings vault, rewrap, vault key wrapping (unreleased)
Items 19 and 20 of the [platform gap analysis](docs/program/PLATFORM_GAP_ANALYSIS_2026-10.md): the shared encryption implementation both editions use. New namespace `RivetCore\Crypto`, all additive, **built in Core only**: no edition has adopted it, nothing changes for an install until it does. No migration (0021 stays free). Decision record: [ADR-011](docs/architecture/ADR-011-envelope-and-key-standard.md); guide with runnable examples: [docs/modules/crypto.md](docs/modules/crypto.md); adoption steps for editions: [UPGRADING.md](UPGRADING.md) "Adopting Crypto".

- **Envelope.** `v3:<kid>:base64(nonce12 || tag16 || ciphertext)`, AES-256-GCM through ext-openssl (**new requirement `ext-openssl`**), the caller's context string (record type and id) as AAD. `Envelope` / `EnvelopeInterface`: `seal`, `open`, `needsRewrap`, `rewrap` (verifies the result), `label`. Typed failures `DecryptionFailed`, `UnknownKeyId`, `KeyUnavailable`, `InvalidKeyMaterial` (all `CryptoException`); never partial plaintext, never `''` for a failure, sealing without a key fails closed. Non-canonical base64 is refused.
- **Keys.** `KeyRing` (kid to 32 bytes, one active, others decrypt-only; weak and duplicate keys refused), `KeyGenerator` (`random_bytes`, `rotate()`, `fingerprint()` with the editions' `rivetit-settings-key-fingerprint|v1|` formula, `ringFromLegacySettingsKey()`), `KeyPurpose` (HKDF-SHA256 labels `settings`, `totp`, `media-token`, `training-pin`, `vault-wrap`, `signing-seal`), `KeyFile` / `KeyRingLoader` / `KeyRingLoadResult` (JSON or PHP array file outside the web root, environment fallback, refuses a world-writable file, warns on world-readable, group-writable, foreign owner and inside-the-web-root, `strict` mode, atomic 0640 write that refuses to overwrite).
- **SettingsVault.** Named secrets bound to their name, per-purpose subkeys from one master KEK, fail-closed, lazy re-wrap (`read()` returns the replacement ciphertext; `decrypt()` hands it to a callback and a failing callback never fails the read), `subkey()` for HMAC keys.
- **Legacy readers.** `LegacySettingsGcmReader` (`ENC2:`), `LegacySettingsCbcReader` (`ENC:`), `LegacyOtpReader` (`enc:` TOTP seeds), `LegacyUserKeyReader` (`V2:`, optionally V1), `LegacyVaultFieldReader` (old credential fields), opt-in `PlaintextPassthroughReader`, factory `LegacyReaders`. - **Rotation and rewrap.** `RotationPlan` (pure), `Rewrapper` with `RewrapSource`, `RewrapItem`, `Reencryptor`, `EnvelopeReencryptor`, `RewrapOptions`, `RewrapReport`, `RewrapState`, `RewrapStateStore`, `FileRewrapStateStore`: resumable, idempotent, compare-and-set writes, dry run, failure and conflict counting, one `crypto.rewrap` audit event per run when an `AuditService` is passed.
- **Vault primitives.** `VaultKeyWrap` (DEK wrap `vw3:<kdf>:<params>:<salt>:<payload>`: Argon2id, else PBKDF2-SHA256 600000+, parameters stored and authenticated, password change = `rewrap()`, instance-KEK wrap for recovery, `openLegacyUserKey()`), `KdfParams`, `VaultCipher` (credential fields in v3 with AAD `credential:<id>[:<field>]`, `migrate()` from a legacy field), `VaultFieldReencryptor` (legacy to v3 and DEK rotation through the `Rewrapper`).

- **Tests and docs.** About 180 new tests (119 unit, 38 kit cases, 23 mutant checks): known-answer vectors from an independent library, NIST/McGrew-Viega GCM test case 16, KDF vectors, tamper/truncation/bit-flip fuzzing, nonce uniqueness, legacy round trips, rewrap resumability and crash recovery, and every example in `docs/modules/crypto.md` is executed. `scripts/bench.php --crypto` (no database needed) and a section in `docs/PERFORMANCE.md`.
