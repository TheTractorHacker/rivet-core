# Windows test plan: endpoint-agent fixes from the 2026-11-15 deep scan (CORE-DS-*)

**Status: UNVERIFIED on Windows.** Every item below was written and `GOOS=windows go vet`/`go build` checked on Linux only; the platform-independent logic has Linux unit tests. Nobody has run these on a real Windows machine. Use the same disposable VM setup as `AGENT_STATE_DIRECTORY_WINDOWS_TEST.md` (administrator `admin1`, standard user `user1`, service `RivetITAgent`, state `C:\ProgramData\RivetIT\Agent`). Record results next to each item.

| ID | What to verify | Result |
|---|---|---|
| CORE-DS-11 | Install agent A (previous release), let it self-update to the new build. Before the update, as `user1`: `mkdir C:\ProgramData\RivetIT\x`. After the swap the new agent refuses the state directory; expect it to exit 75 up to 3 times and then roll back to `rivetit-agent.exe.prev` (the log or Application event shows "new version cannot start; rolled back"), the service runs the old version again and `update.json` reads `rolled_back`. Also confirm a normal update (no planted folder) still confirms and drops `update.json`. | not run |
| CORE-DS-5 | Offer a Windows PC two updates where one installs and one cannot (a driver that needs a EULA, or a deliberately failing KB). Run `patch_install` for both. Expect the job output to list BOTH per-update results (`installed` or `needs_reboot` for the first, `eula_required` or `failed` for the second) and `reboot_required`, with the job itself failed; NOT a bare `{"detail":"scan_failed"}`. The server's history must show the first update as installed. Repeat with `mode: dry_run` and one EULA update. | not run |
| CORE-DS-12 | Run a library script with a `secret` parameter (for example a script that writes `$pw` to a file) on a PC with Security 4688 command-line auditing and PowerShell script-block logging on. Expect the script to see the value, and that neither the 4688 command line (`-EncodedCommand ...` decoded) nor the 4104 script blocks contain the secret or a `FromBase64String` prelude. Also confirm a parameters object over about 30000 characters is refused with "job parameters too large", and that plain string, integer and boolean parameters still arrive as `$name` variables and in `$Params`. | not run |
| CORE-DS-13 | As `user1` own `C:\Users\user1\drop`. From the console run a `file_put` to `C:\Users\user1\drop\x.bin` while `user1` loops `ren drop drop2 & mklink /J drop C:\Windows\Temp`. Expect: the put either lands in the real folder or fails with `temp_failed`; nothing is ever written under `C:\Windows\Temp`. While a large put is running, `ren C:\Users\user1\drop drop2` (and renaming `C:\Users\user1`) must fail with a sharing violation. Also check a normal put (and overwrite=true) through a path containing an ancestor junction/symlink still works because the policy resolves it first. Known remainder: the temp file still inherits the folder ACL (byte-swap variant of CORE-7 not closed). | not run |
