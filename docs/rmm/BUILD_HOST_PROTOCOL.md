# Local agent builds: the build host protocol (spec, 2026-10-19)

Goal: build a new endpoint agent version (Windows exe and MSI template) from the Core source on a machine the owner controls, started from the web UI, with NO compiler or Docker on the web server and NO inbound connection to the build machine. GitHub Actions stays available as the other provider ("Build on GitHub"); this is "Build on my build host".

## Roles
* **Server** (an edition): stores build requests, authenticates the build host, accepts the uploaded files, verifies them, publishes them through the existing binary / MSI template code (same validators and audit as the upload form).
* **Build host**: any Linux machine with Docker (and git) that can reach the server over https. It runs `endpoint-agent/scripts/build-host.sh` from a systemd timer or cron every minute. It only makes outbound requests (pull model).

## Authentication
The server gives each build host a **build host token** (created in Administration > Endpoint agent > Agent updates > Local build > Add build host; shown once; stored hashed with a per-token salt; revocable; has a name, last seen, last IP, enabled flag). The token authenticates `Authorization: Bearer <token>` on the build endpoints ONLY and grants nothing else. Every call is rate limited and audited.

## Endpoints (flat names under the edition's existing API prefix; JSON in and out; all POST)
1. `poll` `{host_version, capabilities:{docker:true, msi:true}}` -> `{job:null}` or `{job:{id, version, source_ref, targets:["windows-amd64","windows-arm64","linux-amd64","linux-arm64"], msi:true, linux?:true|false, expires_at}}`. `linux` is an optional hint (additive; hosts treat a missing value as "decide from `targets`"): `false` means do not build or upload the Linux files, `true` means upload them even if `targets` lacks a linux entry. The server hands out at most one job per host and marks it `claimed` for a lease (15 min, renewable by `status`).
2. `status` `{job_id, state:"building"|"uploading"|"failed", note}` (note capped at 500 chars, escaped on output). A `failed` state carries a log tail (last 4 KiB, secrets masked by the script).

   **Progress fields (optional, additive; a server that ignores them and a host that omits them both keep working):**
   * `stage`: one of `prepare`, `clone`, `build_windows_amd64`, `build_windows_arm64`, `msi`, `verify`, `upload`.
   * `pct`: integer 0-100, overall progress. It never decreases within a job and is 100 on the last status before `complete`. Suggested weights: prepare 0-5, clone 5-10, build_windows_amd64 10-40, build_windows_arm64 40-60, msi 60-80 (a job without `msi` skips the stage and moves to 80), verify 80-85, upload 85-100 (moves per uploaded chunk of ALL files, Linux ones included; the seven stages and the weights are unchanged, the upload band just covers more chunks).
   * `detail`: at most 120 printable characters, for example `chunk 7 of 23`. Display text only: the server escapes it on output. Never secrets.
   * `elapsed_s`: integer seconds since the host claimed the job.
   Stages occur in the order above and never go back. The host sends a status at every stage start and finish, at least every 15 s while a long step runs (this also renews the lease) and after every uploaded chunk. A failed progress status never fails the build; the host retries quietly and goes on. Servers should reject out-of-range values with 400 and may clamp a decreasing `pct`; the reference mock rejects it. `failed` statuses may carry the progress fields too. A status sent after `complete` is refused (the job is `built`), so the final 100 is sent before `complete`.
3. `upload` chunked so it works under PHP's default 2 MiB limits: `{job_id, name, index, total, sha256_chunk, data_b64}` with chunks of at most 1 MiB raw. `name` is one of the fixed file names `rivetit-agent-windows-amd64.exe`, `rivetit-agent-windows-arm64.exe`, `rivetit-agent-windows-amd64.msi`, `SHA256SUMS`, and (additive, 2026-10-20) the Linux agent files `rivetit-agent-linux-amd64`, `rivetit-agent-linux-arm64` (ELF executables), `install-linux.sh` (the installer, a shell script) and optionally the tarballs `rivetit-agent-linux-amd64.tar.gz`, `rivetit-agent-linux-arm64.tar.gz`. The host uploads the Windows files first, then the Linux files, and `SHA256SUMS` LAST; `SHA256SUMS` and the `complete` manifest list exactly the files the server accepted. The server stores the Linux files for the Add device page's one-line install (download from the server, verify, install), runs only the ELF header and hash checks on them, and never executes them.
   **Older servers.** A server that does not know the Linux names answers the first chunk of such a file with HTTP 4xx (400/403/404/409/415/422, error `unknown_file`). The host then logs a warning, skips that file (no more chunks), leaves it out of `SHA256SUMS` and the manifest, and finishes the job, so an older edition still gets its Windows files. Only a refusal of the FIRST chunk of a Linux name is tolerated; any other failure still fails the job. Tarballs are uploaded only when the host config sets `UPLOAD_LINUX_TARBALLS=1`. The server reassembles into a quarantine area owned by the job, never executes anything, enforces per-file and per-job size caps, and refuses names outside the list.
4. `complete` `{job_id, manifest:{files:{name:sha256,...}, commit, go_version, built_at}}`. The server recomputes every SHA-256 over the reassembled bytes, compares them with the manifest and `SHA256SUMS`, runs the existing PE / architecture / MSI-template validators (for the Linux files: ELF magic, 64-bit little-endian, machine x86-64 = 0x3e / aarch64 = 0xb7, size caps, `install-linux.sh` begins with `#!`), checks the version string inside the binary equals the requested version when the validators can read it, and only then publishes (ring and rollout from the request, or "publish when built" as chosen) through the existing publish code. Any mismatch stores nothing and marks the job failed.

## Server rules
* Version: same checks as GitHub builds (format X.Y.Z or X.Y.Z-suffix, not already published, higher than the latest, no second running build for the same version).
* `source_ref` is chosen by the administrator from a fixed list the BUILD HOST declares in its own config (default `main`; tags `v*`/`agent-v*` allowed); the server only forwards the label. The build host refuses any ref not in its own allowlist.
* Job states: queued, claimed, building, uploading, verifying, built, published, failed, expired, cancelled. An administrator can cancel. Jobs expire after 60 minutes without status.
* Nothing from the upload is ever interpreted by the server except hashing and the existing validators; display text is escaped; no path comes from the host (names are from the fixed list; storage names are random).
* The existing GitHub provider keeps working; the UI lets the admin choose the provider per build.

## Build host script (`endpoint-agent/scripts/build-host.sh` + `build-host.service` + `build-host.timer` + README)
* Config file (root or the service user only, mode 0600): `SERVER_URL`, `TOKEN`, `CORE_REPO` (local clone path or git URL), `ALLOWED_REFS`, `WORKDIR`, `GO_IMAGE` (default from go.mod), `MSI_IMAGE`.
* Each run: `poll`; on a job, `git fetch` and check out the ref into a clean temp worktree, run `make dist VERSION=<v> COMMIT=<sha>` and `make msi` in Docker as an unprivileged user (no host network needed after module download, `--read-only` where possible, CPU/memory limits, timeout 25 min), verify its own outputs (Windows PE headers; Linux ELF magic, class, machine and version string; `install-linux.sh` shebang and `bash -n`; size caps: 64 MiB per binary or tarball, 256 KiB for the script), write `SHA256SUMS`, upload chunk by chunk with retries, then `complete`. Clean up on every exit path. Never log the token. Lock file so only one build runs at a time.
* Also `build-host.sh --register` (prints a one-line status), `--once` (single poll, for cron), `--dry-run` (builds, does not upload).
