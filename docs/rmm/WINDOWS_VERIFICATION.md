Date: 2026-10-14 (UTC), run by Claude Sonnet 5.5 for the owner, on the owner's own laptop, driven from the RivetIT **beta** site (`mw-itflow.foleyit.com`, RivetCore `1.0.0-rc.18`).

**Until this day the Windows half of the agent had only been cross-compiled and `go vet`-clean.** The README banner "has never been executed" was true; it is replaced by this page.

## Result in one paragraph

The signing, job execution, SYSTEM context, self-update, service and process tools, file transfer, event-log collector, log rules, alert lifecycle, policy delivery and threshold evaluation all work on a real Windows 11 machine. The run found **eight defects** that no Linux test could show: **six in the agent** (F1 to F4, F6, F7), **one in the server** (F8) and one in four starter scripts (F5). All were fixed, tested where a test is possible off Windows, and the fixes were then re-verified on the laptop with agent 0.7.1. The most serious: **a junction inside an allowed folder escaped the file-transfer path policy** (a real read of `C:\Windows\System32\drivers\etc\hosts` through `...\verify\jn\hosts` succeeded on 0.6.0), and **every script that called a native program (`whoami`, `ping`, `w32tm`, `powercfg`, `quser`, `eventcreate`, ...) silently produced wrong output while the job still reported success**.

Output excerpts are trimmed and contain no secrets; SHA-256 values in job output are masked by the server's redactor (any 64 hex characters), so hashes were compared in upper case or in the transfer ledger.

## Observations that are not defects (or not fixed)

* **Exit code 75 on self-update.** The agent leaves with exit code 75 so the service manager restarts it. The Service Control Manager logs that as an error (events 7031 and 7024 "terminated unexpectedly") in the System log on every update, which a log rule on System errors will see. Not changed; a clean service stop followed by the SCM recovery action, or the updater re-launching itself, would avoid it.
* **Job order within one second.** The queue sorts by `created_at` (one-second resolution) then random `job_id`, so jobs submitted together may run in any order (two file puts to one path ran in the reverse order). Submit dependent jobs one after another.
* **Server redaction masks SHA-256.** `Redactor` masks any 64 lower-case hex characters in job output, so `file_get` / `file_put` results show `"sha256":"[REDACTED]"`. The transfer ledger keeps the real value.
* **`C:\ProgramData\RivetIT\...` can never be a transfer folder** (deny list), which is intended.
* **Laptop clock.** Not an RMM defect: the laptop's clock was already 2 minutes slow and unsynchronised (`Source: Local CMOS Clock`, Group Policy 1129 errors in the System log: no domain controller reachable). The `w32time` restart did not cause it (it is a restart of a client that was not syncing) but the state before the restart was not recorded.
* **Cron is disabled on the beta site** (`Cron: is not enabled`), so housekeeping, including the log-rule recovery sweep, did not run by itself; the sweep was called by hand and closed the alert as designed.
* **Library Defender scripts** in an existing library keep the old text until the pack update is installed (`Starter pack`, "updated" items) on the edition.

## Rollback

Agents never downgrade (`ErrDowngrade`). To withdraw a bad release: in Administration, Endpoint agent, Releases, switch the release off (`rollout 0` or inactive) so no more devices take it; the devices already on it need a **newer** version number. Build the previous source with a higher number (`make dist VERSION=0.7.2` from the commit of the version you want) and publish it. The release rows of 0.6.0 (`release_id` 5 and 6) and 0.5.0 stay in the table for reference. The updater verifies the new binary with `selftest` and rolls back by itself when it does not become healthy.
