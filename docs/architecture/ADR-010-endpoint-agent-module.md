# ADR-010: RMM module (the endpoint agent becomes Core's first RMM area)

Status: FINAL for Phase 0, 2026-10-07: implemented in Core by tasks T1 to T6 and finalised with T5. Owner decisions applied: the extraction is a faithful PORT of RivetIT's code with fix-ups where the original was wrong (each one is listed in the CHANGELOG); behaviour is byte-identical to the recorded golden transcripts; the module's types are `@api` (decision 9 below was changed accordingly). The open points of [the design](../design/endpoint-module-extraction.md) (D1 to D15) that concern the editions (RivetMSP branding, whether the first tag is a release candidate or 1.1.0) stay with the owner and do not change the code.
(The file name keeps the original "endpoint-agent" wording so links stay stable; the decision is about the **RMM module**.)

## Context

RivetIT (v26.10.26) contains a built-in endpoint agent: 20 PHP classes (`src/EndpointAgent/`), a Go Windows agent (`endpoint-agent/`, own CI, `agent-v*` tags), five device REST endpoints and one technician endpoint, admin and device pages, 10 `endpoint_agent_*` tables (DB 2.6.145/2.6.146), signed jobs/checks/updates, MeshCentral remote access and an alert-to-ticket path. RivetMSP has the same RMM tables (`asset_rmm_links`, `rmm_alerts`, `rmm_integrations`, `rmm_scripts`, `rmm_remote_sessions`) and the same `module_rmm*` permission names, but no agent and no Metrics subsystem. The owner wants the agent in Core so both editions use it, and wants it to grow into a complete RMM that is switchable because of its compute cost.

ADR-002 says Core abstracts only what is actually shared and that edition tables (`assets`, `clients`, `users`, `rmm_*`) are reached only through contracts. ADR-003 provides `AccessPolicyInterface`. ADR-004 freezes the API at 1.0 and makes `@internal` types free to change; any new `@api` surface restarts the soak.

## Decision

1. **Core gains an off-by-default module `RivetCore\Rmm\*`.** The existing endpoint code becomes its first sub-area, `Rmm\Agent\*` (enrollment, devices, check-in, update, installer, binaries), beside `Monitoring` (checks, alerts), `Automation` (jobs; later scripts and schedules), `Remote` (MeshCentral launch). Reserved, not built now: `Inventory`, `Policy`, `CustomFields`, `Patching`, `Software`, `Logs`, `Reporting`. The module follows the house style: `declare(strict_types=1)`, storage only through `DatabaseInterface`, no mysqli or superglobals under `src`, additive idempotent migrations that create only Core-owned tables, PHPStan level 6.
2. **Core owns the 10 `endpoint_agent_*` tables, unchanged.** Migrations `0014` (exact current DDL, `CREATE TABLE IF NOT EXISTS`, collation `utf8mb4_general_ci`), `0015` (guarded convergence for installs that stopped at RivetIT 2.6.145) and `0016` (additive switch/capacity columns). No renames, no credential or key format changes, same wire protocol, same signing vectors (one source of truth in `endpoint-agent/testdata/vectors/`, read by Go and PHP). A schema-diff test (reference DDL versus fresh Core versus upgraded) is the proof of compatibility.
3. **Editions implement four required contracts and reuse existing ones.** Required: `RmmTenancyInterface` (clients, locations, per-user client scope), `RmmAssetsInterface` (asset match/create/fill/move), `RmmBridgeInterface` (the edition's RMM tables: integration row, link rows, alerts with ticket auto-close, saved scripts, remote-session log), `SecretBoxInterface`. Optional or defaulted: `RmmMetricSinkInterface` (null sink; RivetMSP has no Metrics), `RmmAuditInterface`, `RmmModuleStateInterface`; `RmmEventsInterface` joins in Phase 1. Reused: `DatabaseInterface`, `AccessPolicyInterface` (nine abilities: `rmm.device.view`, `rmm.job.run_saved`, `rmm.job.reboot`, `rmm.job.run_script`, `rmm.remote.launch`, and the administrative `rmm.device.manage`, `rmm.token.manage`, `rmm.binary.publish`, `rmm.admin`; RivetIT maps the last four to `role_is_admin`), `ClockInterface`, `UrlPolicy`, `JobQueue`/`JobWorker`, `Redis\RateLimiter`. Authorization for acting stays an edition policy (ADR-002/003); Core never encodes an edition's roles.
4. **HTTP is framework-neutral.** Core ships `RmmRequest`/`RmmResponse` value objects and `DeviceApi`/`TechnicianApi` handlers; the editions' `api/v1/agent_*.php` files shrink to bridges that build the request, call Core and emit the response. TLS-proxy trust, CSRF, sessions, HTML, navigation and permission wiring stay in the edition. Core ships **data, not markup** (read models and validated admin operations); each edition renders its own pages.
5. **The Go agent and its CI move to the Core repo** (`endpoint-agent/`, workflow `endpoint-agent.yml`, tags `agent-v*`, releases on rivet-core). The Composer dist archive excludes it (`export-ignore`), because both editions commit `vendor/`. Binaries still reach customers through the edition: the administrator uploads (or later fetches) the release asset into the edition's binary store and endpoints download from the edition host, never from GitHub. Agent-visible identity (service name, install path, `rivetit-agent-*.exe`, `RIVETIT-EMBED-v1`, `rivetit:<id>`, `rivetit_agent`) is **not renamed** in this ADR.
6. **Extensibility is built into Phase 0, features are not.** A job-type registry (PHP and Go) seeded with the three existing job types; a reserved capability block in check-in (additive, old agents treated as today's Windows agent); per-OS collectors behind the existing `collect.Platform` interface; a policy assignment model (client, site, group, tag, device, with inheritance) whose first bundle kind is today's signed check list. Later areas arrive as companion interfaces, never as new methods on Phase 0 interfaces (ADR-004).
7. **The module is switchable and costs nothing when off.** Master switch OFF by default for new installs; for existing RivetIT installs it is the existing `endpoint_agent_settings.enabled` value, never inferred from data; RivetMSP adds `config_core_rmm_enabled` (default 0) following its `CoreBridge` convention. Sub-switches (`monitoring`, `metrics`, `jobs`, `remote`, `updates`, later the new areas) live in `endpoint_agent_settings.features_json`. When off: a pre-bootstrap gate in the edition's API front controller answers device endpoints **503 `module_disabled` with `Retry-After: 3600`** from a state file with no database connection or query, no cron work, no navigation, no handlers; data is kept and re-enabling resumes. Agents back off (the existing agent already treats 5xx plus `Retry-After` as transient; a new branch removes any data loss). This is the only intentional wire-visible change in Phase 0.
8. **Compute is budgeted.** Limits (max devices, interval floor/ceiling, global check-ins per minute, body caps, pruning in batches), optional queued ingestion through `JobQueue` with a separate low-priority worker, load shedding with hysteresis (stretch intervals, then 503 + jittered `Retry-After`), new-install defaults that cut write volume (collect 300 s, 7-day raw retention), an administration "Performance and capacity" panel with one-click presets, and a load-test plan with numeric gates (rc: 500 devices; GA: 5,000 devices; disabled mode: zero queries).
9. **Release vehicle.** Owner decision: the module's types are **`@api`** from the start (the contracts, `RmmModule`, the request/response objects, `RmmAbility`, the services and read models editions call, `Signer`/`CanonicalJson`/`InstallerStamp`, the conformance kit); only the migrations (`Migration\*`, `RmmSchema`) and the in-memory reference adapters stay `@internal`. The consequences are on the table: `docs/api-surface.md` grows, and under `docs/RELEASE_GATE.md` any new `@api` surface restarts the 1.0 soak, so the module ships with the next tag whichever it is (a release candidate or 1.1.0, the owner's call). The migrations are in `CoreMigrations::all()` (all three are no-ops on an install that already has the tables).
10. **Order of operations:** baseline and golden transcripts; Core contracts and migrations; pure classes and vectors; services and handlers; Go move; module switch and capacity; RivetIT adopts behind identical REST behaviour and deletes `src/EndpointAgent/`; RivetMSP adopts; promotion in 1.1.0. Nothing is pushed, tagged or released by implementation agents.

## Consequences

* Both editions share one agent, one protocol and one fix stream; a Core fix reaches both. The price is coupling (mitigated by the frozen-constants test, the vectors and the additive-only compatibility rule in `docs/rmm/PROTOCOL.md`).
* Each edition keeps one adapter set (about six small classes). RivetMSP's adapters are near copies of RivetIT's because both editions share the fork schema; a Core-shipped reference SQL adapter was considered and rejected by default (it would put `assets`/`asset_rmm_links` SQL in Core, contradicting ADR-002). The conformance kit keeps the adapters honest.
* `Rmm\*` is `@api` (owner decision): a later change to it follows ADR-004, and editions pin an exact tag until the soak ends.
* Existing RivetIT installs keep working without action: tables, credentials, keys, enrolled agents and the enabled state are untouched; the 2.6.145/146 migration steps remain as idempotent history and a new step only runs Core's runner.
* The disabled-server response changes from 403 to 503 (decision D12); old agents already back off on 5xx.
* A complete RMM (policies, patching, software deployment, macOS, native remote, log collection) is a multi-quarter programme. Phase 0 must ship alone; every later phase is a separate release behind its own sub-switch, off by default, with its own design addendum and its own security review.
* New work for Core's quality gates: a module page (`docs/modules/rmm.md`), a protocol document, threat-model additions (device authentication, SYSTEM-level job execution, remote access) and a focused security review before promotion to `@api`.

## Decisions taken while implementing Phase 0

* **Authorization abilities** grew from six to nine (see decision 3) so an edition can split the administrative grants later; the technician identity is a minimal `Authz\RmmPrincipal` (user id and display name). Roles, module-only logins and the client scope stay in the edition's policy and tenancy and are asked on every call.
* **No new contract was added.** The installer's base URL is the module's own `service_url` setting; alerts are not read through the bridge (the device read model exposes each check's `alert_id` and the edition joins `rmm_alerts` itself); the MeshCentral probe takes the existing `UrlPolicy`.
* **Windows binaries only are hosted.** `endpoint_agent_binaries` has no platform column and a migration for it is not part of Phase 0, so the Linux agent is installed from its release tarball with `install-linux.sh` (the deployment snippet does that); `BinaryStore::detect()` identifies PE and ELF headers.
* **Fix-ups of the original** (each has a test and a CHANGELOG line): the technician list's `total` and status filter, the 500-device ceiling of the administration page's counters and approval queue, a trailing newline accepted in a MeshCentral node id, an unbounded technician request body, a MeshCentral probe pinned to one address only, a transfer that did not check the target client against the caller's scope, a non-atomic "make current".

## Alternatives considered

* **Leave the agent in RivetIT and copy it to RivetMSP.** Rejected: two diverging copies of a signing and remote-execution surface.
* **Core ships HTML/UI.** Rejected: couples Core to an edition's CSS and layout; editions differ (`admin/` and `agent/` layouts).
* **Core ships a SQL adapter for the shared edition schema.** Rejected by default (above); owner decision D3.
* **Put the module in a separate package (`rivet/rivet-rmm`).** Not chosen: one repository, one tag and the conformance kit are simpler while the surface is small; ADR-009's "split above about 20 files" trigger applies here too, and the module will exceed it, so revisit at the 1.1 promotion.
* **Switch stored in the edition `settings` table.** Rejected for RivetIT (row-size limit) and unnecessary: the module's own one-row table already holds the master switch and works the same in both editions; only RivetMSP adds its conventional `config_core_rmm_enabled` kill switch.
* **Renaming the agent and its identifiers now.** Rejected: they are identity for self-update and installed devices; a neutral rebrand is a separate migration project with a dual-name period.

## Reversal cost

Before RivetIT adopts (steps 1 to 6): none beyond deleting Core files. After adoption: moderate; the tables never moved and the PHP classes are replaceable by git revert, because the wire protocol and schema were deliberately left identical. After promotion to `@api`: governed by ADR-004 (a major).
