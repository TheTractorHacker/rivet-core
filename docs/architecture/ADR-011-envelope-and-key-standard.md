# ADR-011: One encryption envelope and key standard for both editions

Status: accepted (2026-10-10). Implements items 19 and 20 of the [platform gap analysis](../program/PLATFORM_GAP_ANALYSIS_2026-10.md) in Core.

## Context

RivetIT and RivetMSP each carry their own copy of the encryption code, and the copies have drifted into five formats:

| Format | Where | Problem |
|---|---|---|
| `ENC:` base64(iv16 or ct), AES-128-CBC, key = first 16 bytes of sha256(config string) | settings | unauthenticated; a flipped bit decrypts to garbage unnoticed |
| `ENC2:` base64(nonce12 or tag16 or ct), AES-256-GCM, key = sha256(config string) | settings | authenticated, but no key id (a rotation cannot be told from a corruption), no AAD (a ciphertext can be moved to another setting) |
| `enc:` iv16 + base64(ct), AES-128-CBC, key = the vault master key | TOTP seeds | unauthenticated, tied to a logged-in vault session |
| `V2:` salt16 + iv16 + base64(ct), AES-128-CBC, PBKDF2-SHA256 100000 iterations to 16 bytes | per-user wrap of the vault master key | 128-bit keys, 100k iterations, unauthenticated |
| iv16 + base64(ct), AES-128-CBC, key = the 16-character master key string | credential fields | a 16-character base64url string (about 96 bits) is the key of every credential; unauthenticated |

Two copies of the settings cipher also behave differently on failure (the old one stored cleartext without a key, the new one returns
`''` on any error, which callers mistake for "not configured"). Backups copied the key next to the data it protected.

## Decision

1. **One envelope.** `v3:<kid>:base64(nonce12 || tag16 || ciphertext)`, AES-256-GCM, via ext-openssl (always present, runs on PHP 8.2 and
   later; libsodium's AES-GCM needs CPU support and is not used). Standard padded base64, and only the canonical spelling is accepted.
2. **Key id (`kid`) in the value.** The reader picks the key by name. A value sealed under a retired key says so (`UnknownKeyId`), a
   rotation is "add a key, make it active, rewrap, retire", and the rotation panel can count values per key.
3. **AAD is the caller's context string** (record type and id, for example `credential:42:password`, `settings|smtp_password`). A
   ciphertext moved to another record, field or setting does not authenticate. An empty context is a programming error. AAD is not
   encrypted or stored; the reader must know it, which is what makes it a binding.
4. **GCM, not CBC plus HMAC or a stream construction.** One primitive that authenticates, available everywhere, with standard
   test vectors (the unit tests include NIST/McGrew-Viega test case 16 and vectors generated by an independent library). Costs: a
   96-bit random nonce per message, so a key must stay under about 2^32 messages; per-purpose HKDF subkeys and rotation keep every key
   orders of magnitude below that. Nonce reuse under one key would be catastrophic for GCM, so the nonce source is `random_bytes` and the
   only way to fix it is a constructor argument marked test-only.
5. **Typed failures, no partial plaintext, no `''` for failure.** `DecryptionFailed` (cause deliberately indistinguishable),
   `UnknownKeyId`, `KeyUnavailable` (also thrown when sealing without an active key: **fail closed, never store cleartext**).
6. **Key hierarchy** (matches the gap analysis table):
   - **KEK**: 32 random bytes per kid, in a **root-owned file outside the web root** (`root:www-data`, mode 0640). The loader refuses a
     world-writable file, warns on world-readable, group-writable, foreign owner and inside-the-web-root, and falls back to the
     environment only when no file exists. Created by `random_bytes`; weak or repeated keys are refused.
   - **Subkeys**: HKDF-SHA256 from the KEK with the purpose in the info string (`settings`, `totp`, `media-token`, `training-pin`,
     `vault-wrap`, `signing-seal`). A leak of one derived key does not reveal the KEK or the other purposes; a value cannot be opened under
     another purpose.
   - **Vault DEK**: 32 random bytes encrypting credential fields in the v3 envelope (AAD `credential:<id>[:<field>]`). It is wrapped
     once per user under a key derived from the user's password and once under the KEK (the recovery path: the KEK can re-issue a
     user's wrap). A password change re-wraps the DEK and touches no credential.
   - **Password KDF**: Argon2id (libsodium, 64 MiB x 3 by default) when available, else PBKDF2-HMAC-SHA256 at 600000 iterations. The
     parameters are stored in, and authenticated by, the wrap (`vw3:<kdf>:<params>:<salt>:<payload>`), so they can be raised later and a
     lower-than-minimum or absurdly high value is refused rather than trusted.
7. **Legacy formats stay readable** through `LegacyReader`s that reproduce the editions' functions faithfully (`ENC:`, `ENC2:`, `enc:`,
   `V2:` and the old credential field), are tested against samples written by the editions' own function bodies (copied verbatim into a
   test fixture), and **fail closed** where the editions returned `''`. Reading cleartext legacy values is an explicit opt-in
   (`PlaintextPassthroughReader`). Legacy values are re-wrapped lazily on read (`SettingsVault` hands the replacement ciphertext to a
   callback) and in bulk by the `Rewrapper`.
8. **Rewrap is a service, not a script.** `Rewrapper` walks an edition-supplied `RewrapSource` in pages with a compare-and-set write, saves
   its cursor after each batch (resumable), is idempotent, supports a dry run that writes nothing, counts unreadable values and lost
   races instead of aborting, and logs one `crypto.rewrap` audit event per run. Progress goes through a `RewrapStateStore`; **no Core table
   or migration is needed** (a file store and an in-memory store ship; an edition can keep the serialised state anywhere).
9. **Fingerprints, not keys, in manifests.** `KeyGenerator::fingerprint()` keeps the editions' constant
   `rivetit-settings-key-fingerprint|v1|` so existing backup manifests and `backup.sh` agree.

## Where keys live, rotation and backup

- **Location.** `/etc/<product>/keys.json` (or similar), outside the web root, `root:www-data` 0640. The edition passes the path to
  `KeyRingLoader`. Docker: a mounted file or secret.
- **Rotation.** `KeyGenerator::rotate()` adds a key with a new kid and makes it active; old keys stay decrypt-only. Run the rewrap
  (dry run first, then real; repeat until it reports 0 rewrapped); `RotationPlan` says what is left and which kids no value uses any more.
  **Keep a retired key for one full backup cycle**, then remove it from the file and take a fresh offline copy. A value naming a missing
  kid is `UnknownKeyId`, and `RotationPlan` reports it as a blocker before anything is retired.
- **Backup and escrow.** The key file is backed up **offline and separately** from the database dump and from the backup passphrase: if
  all three share a copy, encrypting the dump protects nothing. The backup manifest records `fingerprint(kid)` per key so a restore can
  verify it has the right file before it starts. Losing the key file loses every value sealed under it; there is no backdoor. Escrow is
  an offline copy held by a second named person.
- **Vault.** A user who forgets their password is re-issued a wrap by an admin through the KEK wrap, not by weakening the KDF.

## Consequences

- Editions delete their private copies and call Core; both get the same fail-closed behaviour and the same tests.
- Existing data moves with no downtime: v3 is written immediately, legacy values stay readable until rewrapped.
- Core now requires `ext-openssl` (every PHP build the editions run on has it).
- Context strings become part of the stored data's meaning: **changing a context string after data is written makes that data
  unreadable.** They are documented in each edition's adoption notes and covered by that edition's tests. The ones Core defines
  (`credential:<id>:<field>`, `<purpose>|<name>` for settings, `vault-dek|<ctx>`, `vault-dek-wrap|...`) are frozen by ADR-004.
- Not addressed here (still in the gap analysis): the instance signing key sealing (a `signing-seal` purpose label exists, the use is
  the RMM key-rotation item), a UI rotation panel, and the backup-side changes (items 1 and 12).

## Alternatives considered

- **libsodium secretbox / XChaCha20-Poly1305** (24-byte nonces, no 2^32 limit): better margins, already required for the RMM secret box.
  Rejected for the shared envelope because the editions' existing settings format is AES-GCM, OpenSSL is what their operators' audits
  expect, and the single-key volumes here are tiny. The format is versioned (`v3`), so a `v4` could change this.
- **Deriving the KEK from a passphrase at start-up:** forces a human into every PHP-FPM restart; rejected. The file is root-protected instead.
- **A Core table for rewrap progress:** possible later; not needed now, so no migration number was consumed (0021 stays free).
- **Encrypting AAD into the value:** defeats the point (the reader must independently know what the value is bound to).

## Reversal cost

Low until an edition writes v3 values; after that, reverting means rewrapping back to the legacy formats, which weakens them. The
format prefix is versioned, so improving the envelope is a new prefix with the old one kept readable.
