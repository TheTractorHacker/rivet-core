# Second security review, 2026-10

Scope: all of `src/` at v0.21.0 (branch `security-fixes-2026-10`), ROADMAP item "Second security review plus threat-model
pass" (issue #41), done before 1.0.0-rc.1. It builds on the first hardening pass released as 0.18.1 and does not repeat it.
Companion documents: [threat-model.md](threat-model.md) and [edition-checklist.md](edition-checklist.md).

## Method

Adversarial, attacker-first review of every module named in the ticket (Redis, Webhooks, Mcp, Jobs, Cron, Audit,
Compliance/SharedReport, Retention, KB converters, Knowledge, Migration, Ui, Support/AccessPolicy, Automation), by reading
the code and then proving or disproving each suspicion with a running experiment. Only findings with a concrete trigger path
are reported.

1. **Inventory of dangerous sinks** by grep: every `preg_*` (ReDoS and `$` anchor semantics), every string-built SQL
   (`LIMIT`, `OFFSET`, identifiers, `IN (...)`), `exec`/`proc_open`/`escapeshellarg`, `rand`/`mt_rand`/`uniqid`/`md5`/`sha1`,
   `unserialize`/`eval`/`include`, `libxml`/`DOMDocument`, curl and Guzzle calls, `file_get_contents`/`fopen`.
2. **Data-flow reading** per module: who controls each input (admin, agent, MCP client, receiver, IdP, uploader), where it is
   stored, where it is echoed, and which component re-validates it.
3. **Experiments** (scratch scripts and the regression tests): a 31-URL SSRF battery against `UrlPolicy` (decimal/octal/hex
   IPv4, mapped/compatible/NAT64/6to4 IPv6, userinfo, fragments, ports, zone ids, trailing dots, full-width digits);
   pathological inputs against `CredentialReferenceRenderer` and `EventCatalog::matchPattern` (no ReDoS, tested to 800 KB and a
   70-wildcard pattern); a hostile local receiver streaming 160 MB; oversized MCP arguments through `ToolPipeline` into a real
   strict-mode MariaDB; a PNG header declaring 60 000 x 60 000 pixels; a UTF-16 DOCTYPE inside a DOCX.
4. **Edition spot checks** (read-only) of RivetIT and RivetMSP for the assumptions Core makes (see the checklist).
5. Every Medium-or-higher finding is fixed with a regression test; Low findings are fixed when trivial, otherwise accepted with
   reasoning. Nothing was "fixed" by removing a feature; all changes are backward compatible.

Severity: **High** = remote compromise or cross-tenant disclosure without special privileges; **Medium** = security control
bypass, secret leakage, or reliable denial of service by a low-privileged actor; **Low** = defence in depth, needs an admin or
an unusual configuration, or limited impact. No High or Critical finding was identified.

## Findings

|---|---|---|---|---|
| SR-04 | Medium | Webhooks / `WebhookDispatcher::curlTransport` | A receiver could stream an unbounded response body. curl buffered all of it (`RETURNTRANSFER`) until the 10 s timeout: at gigabit speed that is >1 GB, so a hostile or broken endpoint could kill the PHP process (a fatal error breaks the "never throws" contract and the user action that fired the event), or hold a worker. | **Fixed** |
| SR-05 | Medium | Audit / `AuditService`, Mcp / `ToolPipeline` | Audit evasion by oversized metadata: `metadata_json` is a `TEXT` column. In strict SQL mode a larger value makes the INSERT throw; `ToolPipeline::record` swallows it, so an MCP client sending one huge argument got its (read) call executed with **no audit row**. In non-strict mode the JSON was silently cut and became invalid. | **Fixed** |
| SR-06 | Medium | Audit / `AuditService::log` | The `afterLog` fan-out (webhooks, automation) received the **unredacted** `$metadata`, while only the database copy was redacted. Secrets the edition relied on Core to strip (`password`, `token`, ...) left the trust boundary to external receivers. | **Fixed** |
| SR-01 | Low | Webhooks / `Authentication::isValidHeaderName` | `/^...+$/` matches before a trailing `\n`, so a header *name* ending in a newline passed validation and bypassed the forbidden-name list (`"X-Rivet-Signature\n"`, `"Host\n"`). Admin-only, impact limited to a malformed header line. | **Fixed** (`\z`/D) |
| SR-02 | Low | Webhooks, Redis, Cron, Automation, Compliance | The same `$` anchor flaw in `EventSummary::isSafeUrl`, `Destination::urlMatches`, `RedisConnectionConfig` (host, username), `JobRunner` (arguments, php binary), `AttestationStore`, `AutomationRuleStore`. | SR-11 | Low | Migration / `MigrationRunner` | `GET_LOCK('rivet_core_migrations')` is **server-wide**: migrating database A made an unrelated database B on the same server wait up to 60 s and then fail with "Another Core migration run is in progress". Observed during this review (several agents' suites on one MariaDB timed out). Availability only. | **Fixed** (lock name = `rivet_core_migrations:` + MD5 of the current schema; `LOCK_NAME` constant kept) |
| SR-12 | Low | Automation / `AutomationRuleStore` | `send_webhook` URLs were validated for scheme and host only: userinfo, whitespace, control characters and backslashes were accepted. | **Fixed** for shape; the *address* check remains the edition's send-time `UrlPolicy` (see SR-15) |
| SR-13 | Low | Mcp / `McpDiagnostics` | The "health check" fetches the admin's issuer discovery document and then the `jwks_uri` named inside it: a blind SSRF to any `https` host (status code and a few text hints come back). Exploitable only with an IdP that issues such subjects (mainstream IdPs issue lowercase hex, UUIDs or numbers). | **Edition-action / deferred**: needs a coordinated Core migration (binary collation) and the matching edition column, which cannot ship safely while the migration list is being extended for 1.0. ### Evidence for the fixed findings

**SR-04.** `WebhookDispatcher::curlOptions` set `CURLOPT_RETURNTRANSFER => true` and `curlTransport` returned
`(string) $response`; `CURLOPT_TIMEOUT` is the only bound (curl's `MAXFILESIZE` only works with a `Content-Length`).
Test `testHostileReceiverCannotExhaustMemoryOrHoldTheRequest` starts `php -S` with a router that emits 160 MB, delivers to it,
and asserts status 200, peak memory growth under 16 MB, a logged snippet of exactly 1000 bytes and a short run time. Fix: a
`CURLOPT_WRITEFUNCTION` keeps the first 16 KB and aborts the transfer after 1 MiB (the status line is already known, so the
attempt still reports the real HTTP status). The 1000-byte log snippet is now cut on a UTF-8 boundary (`mb_strcut` after
`mb_scrub`); a multi-byte character split in two used to make the log INSERT fail under strict SQL and the attempt was not
recorded.

**SR-05.** Reproduced in `tests/Integration/SecurityReviewTest::testOversizedMetadataIsStoredAsATruncatedRowUnderStrictSqlMode`
(real MariaDB, `STRICT_ALL_TABLES`): 600 KB of arguments. Before the fix the INSERT threw `Data too long`. After: the row is
stored with the small top-level values kept (`tool`, `outcome`), big ones replaced by `[truncated: N bytes]`, a `_truncated`
flag, and the secret still redacted. Unit twin: `testAuditedToolCallWithHugeArgumentsIsStillRecorded` through `ToolPipeline`.

**SR-06 and SR-07.** `AuditService::log` passed `$metadata` to `afterLog` after storing `redact($metadata)`. Fixed to pass the
redacted copy; tests `testAuditFanOutNeverSeesSecretsAndDeepSecretsAreNotStored` (including a secret 13 levels deep, which was
stored raw before) and `testCompoundSecretKeysAreRedactedButHarmlessOnesAreNot`.

**SR-01/02/03.** `testHeaderNameWithTrailingNewlineIsRejected`, `testTrailingNewlineIsRejectedByUrlAndNameValidators`,
`testCronArgumentsAndPhpBinaryMustMatchExactly`, `testAutomationWebhookUrlMustNotCarryCredentialsOrWhitespace`,
`testEventNameCannotInjectHeaders`.

**SR-08/09.** `testPermissionCheckThatThrowsFailsClosed`, `testLogMessagesAreSingleLine`.

**SR-10.** `ConverterImageLimitsTest::testHugeDeclaredDimensionsAreSkippedButNormalImagesStay` (a 3000x2000 image is kept,
60000x60000 and 40000x1 are skipped with a warning). The same file pins the UTF-16 DOCTYPE case as rejected (it was already
safe through the parsed-document check; the test documents why the byte scan alone would not be enough).

**SR-11.** `SecurityReviewTest::testAMigrationLockHeldForAnotherSchemaDoesNotBlockThisOne`;
`MigrationAndAuditTest::testSecondRunnerGivesUpCleanlyWhileAnotherHoldsTheLock` now holds the lock under the schema-scoped name.

## Reviewed, no finding

Kept here so the next reviewer does not repeat the work.

* **SQL injection.** Every query is parameterised. The only interpolations are integers that are clamped or cast first
  (`AuditReader` `LIMIT/OFFSET`, `JobQueue::heartbeat` placeholder list built from `intval`, `RetentionService` batch size and
  constant table names, `Migration0010Subjects` constant table names).
* **Randomness.** Only `random_bytes` (lock tokens, request ids, converter media tokens, scratch directory names). No `rand`,
  `mt_rand`, `uniqid`, `md5`/`sha1` for security.
* **Deserialisation / code execution.** No `unserialize`, `eval`, `include` of data, dynamic class instantiation from rows, or
  `extract`. Job types and automation actions are lookups into edition-registered handler maps.
* **Signature comparison.** Core only *produces* signatures; the verification snippets handed to receivers use constant-time
  comparisons and a replay window.
* **UrlPolicy.** The battery above (decimal/octal/hex IPv4, `127.1`, `0`, mapped, compatible, NAT64, 6to4, Teredo, userinfo,
  `#@`, zone ids, trailing dots, full-width digits, `nip.io` style names, ports 0 and 99999, newline and CRLF suffixes) all
  behave: either rejected, or allowed to a public address that is then pinned.
* **ReDoS.** All `preg_*` patterns were read; the ones fed hostile input have disjoint alternatives or short bounded inputs
  (`CredentialReferenceRenderer::TAG_PATTERN` tested to 800 KB: linear, with a JIT-stack failure that falls back to the
  unrendered input; `EventCatalog::matchPattern` with 70 wildcards: milliseconds; `PayloadTemplate` lazy `{{ }}` scan is
  bounded by the 8 KB template limit; `JobRunner` patterns run on root-owned cron lines).
* **Template engine.** No evaluation: path regex, closed filter list, encoding-aware escaping, output and placeholder caps.
* **DOCX/PDF.** XXE, entity expansion, zip bomb (declared and actual), zip slip, disguised media, link schemes, no shell in the
  PDF path, scratch directory handling, pipe draining: all hold; the 0.16 corpus plus the new tests cover them.
* **JSON depth bombs.** `json_decode` depth is bounded (`RedisMetadataCache` 32, `AuditReader::decodeMetadata` 64, others use the
  default 512 on data Core wrote).
* **Integer handling.** Clamps on `perPage`, `limit`, `days`, `LIMIT`; `DateRange` clamps to 1970..2099; huge `DateTime::modify`
  offsets do not throw.
* **Authorisation contract.** `DenyAllPolicy` / `AllowAllPolicy` behave as documented; no Core code reads the default policy.
