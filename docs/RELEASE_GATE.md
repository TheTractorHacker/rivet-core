# 1.0.0 release gate

Issue #44. The gate is the list in ROADMAP.md ("What 1.0.0 means" and "1.0.0 release gate") mapped to evidence you can run or read, with
an honest status as of 2026-10-06 (tree after `v0.21.0`). Statuses:

- **done**: the evidence exists and is current.
- **partly**: some of it exists; the gap is named.
- **soak**: needs time in production, nothing to build.
- **VM run**: needs the clean-VM installer run.
- **decision**: needs the maintainer's decision.
- **unverified**: this document could not check it (for example a CI result on GitHub).

Nothing here is a claim that 1.0.0 is ready; the point is to make the remaining work visible.

## Remaining before 1.0.0 final

In order:

1. Sign off `docs/api-freeze-review.md`; make the `compatibility` CI job required (remove `continue-on-error`) in the same commit that follows `v1.0.0-rc.1`.
2. Decide the `mcp_unlinked_identities` collation item (migration before 1.0, or documented deferral).
3. Finish the security documents (`docs/security/review-2026-10.md`, `docs/security/threat-model.md`); close or defer every HIGH and MEDIUM finding in writing; decide on an external review.
4. Add a scheduled weekly `composer audit` workflow (the roadmap asked for one; today it runs on push and pull request only).
5. Re-record [PERFORMANCE.md](PERFORMANCE.md) on a quiet machine and on a CI runner; optionally add a `--check` mode to `scripts/bench.php` that enforces the budgets.
6. Each edition: pin the release candidate, run the conformance kit in its CI, apply the Core migrations to `db.sql`, deprecate the shims, and move RivetIT from `^0.18` forward (it lacks the 0.19 to 0.21 features).
7. Run the clean-VM installer tests (fresh install and upgrade from the previous release) for both editions, plus the browser smoke suites.
8. Complete adoption so every module an edition claims is used for real (RivetMSP consumers, Redis rate limiting, MCP after agent single sign-on).
9. Write the `CHANGELOG.md` 1.0.0 section, fill in the "Between 0.21.0 and 1.0.0" part of UPGRADING.md, and have someone other than the author follow the quickstart on a clean machine.
10. Tag `v1.0.0-rc.1`; start the 30 day soak in both productions; fix only bugs (any API change restarts the clock).
11. When the soak ends with no open P1 or P2 and a green CI on the release commit: move both editions to `^1.0` in a tested change with a rollback branch, tag `v1.0.0`, and let `release.yml` publish the GitHub Release.
