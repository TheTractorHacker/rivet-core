# Edition prompts: RivetCore 1.0.0-rc.67 (Mesh node mapping: reasons, bulk approve, verified auto-map)

Core can now say exactly why a device is not mapped to a MeshCentral node, approve many devices at once, and (opt-in) let MeshCentral itself confirm a node. Read `docs/rmm/REMOTE_AND_LOGS.md` ("Mesh node mapping") and the rc.67 CHANGELOG entry first. **Migration `0052_rmm_mesh_verify` is new** (two nullable text columns: `endpoint_agent_mesh_settings.verify_json`, `endpoint_agent_mesh_agents.verify_json`); run the Core migrations in ONE DB step and mirror both columns in the edition's schema file. Numbers 0050 and 0051 belong to other open changes: apply them in order. Nothing here changes the device protocol, the installer file or an existing signature: every new constructor argument is an optional trailing one.

What Core does now, so the prompts can stay short:

- `TechnicianActions::meshMapping($who, $deviceId)` / `GET endpoint_devices/{id}/mesh/mapping` (the default device detail does NOT carry it: call this from the device page) give `{state, reason, reported_node_id, mapped_node_id, mapped_source, conflict_device_id, can_approve, verification}`. States: `not_installed`, `installed_no_node_reported`, `reported_needs_approval`, `conflict`, `kept_manual`, `mapped`. Show `reason` as is (it already carries the "has not been approved yet" text for `reported_needs_approval`).
- `TechnicianActions::meshMappings(RmmPrincipal $who, array $filters = [], int $limit = 100, int $offset = 0)` and `GET endpoint_devices/mesh/mapping` return `{items, total, counts, limit, offset}` for the caller's clients only (`state`, `client_id`, `q` filters). `can_approve` is already false where the caller lacks `rmm.device.manage`.
- `TechnicianActions::approveMeshNodes(RmmPrincipal $who, array $deviceIds)` and `POST endpoint_devices/mesh/approve {"device_ids":[...]}` (max 200) map the node each device REPORTED (a typed node is not accepted) and answer `{requested, changed, skipped, refused, results:[{device_id, result, code, message}]}`. A conflict is never overridden.
- `RemoteActions::meshVerifySettings(RmmPrincipal)` / `updateMeshVerifySettings(RmmPrincipal, array)` and `GET`/`PUT endpoint_devices/mesh/verify` (administrators): `mesh_verify_nodes` (off by default), `mesh_service_account`, `mesh_group_map` (client id => Mesh device group id; the group id may be pasted in any spelling Core already accepts). The housekeeping job does the verification; there is nothing for the edition to schedule.
