# Edition prompts: RivetCore 1.0.0-rc.59 (device move completeness; installer: managed by another RMM)

Core changed two things an edition has to adopt. Read `docs/modules/rmm.md` (sections "Moving a device to another client" and "Installer option: managed by another RMM") and the rc.59 CHANGELOG entry first. Migration `0049_rmm_installer_managed_externally` is new (one additive column); run the Core migrations and mirror it in the edition's schema file. Nothing here changes the device protocol, the installer file or any existing signature: every new parameter is an optional trailing one.

What Core does now, so the prompts can stay short:

- `TechnicianActions::transfer(RmmPrincipal $who, int $deviceId, int $clientId, int $locationId = 0): ActionResult` checks `rmm.device.manage` on the old and on the new client, then moves the device, its asset, open alerts, all its jobs, patch, package, deploy and transfer state and its stored logs and changes to the new client in one transaction. The credential, `install_id` and the agent link are untouched, so the machine keeps checking in without re-enrolling. Moving to the client it is already in is a no-op. A retired device can be moved.
- `TechnicianActions::setAutomationDisabledBulk(RmmPrincipal $who, array $deviceIds, bool $disabled, ?int $clientId = null): ActionResult` sets or clears the same switch on existing devices. It checks `rmm.device.manage` per device, reports devices it may not touch as `skipped` (identical for missing and foreign ones) and returns `data` with `changed`, `unchanged`, `skipped` id lists and `counts`; at most 500 devices.
- `TechnicianActions::createToken(..., bool $managedExternally = false)`, `RmmAdmin::downloadInstaller(..., bool $managedExternally = false)` and `RmmAdmin::deploymentCommands(..., bool $managedExternally = false)` store the choice by token; every device enrolled with it starts with Core automation off (`device_automation_disabled = 1`) and an audit row says why.

## RivetIT chat

```
Adopt RivetCore 1.0.0-rc.59 and add two UI features. Worktree, one PR, beta first, dump the database before the migration, do not deploy to production.

0. Pin rivet/rivet-core to the rc.59 tag, run Core migration 0049 in ONE DB step and mirror it in db.sql (endpoint_agent_installer_options.managed_externally tinyint(1) NOT NULL DEFAULT 0). Do not bump or re-pin UI assets unless you touch CSS.

1. "Move to Department" action. On the asset edit modal and on the device page (visible only when the asset has an endpoint device, and only to users who hold the Core ability rmm.device.manage) add a "Move to Department" button. It opens a small dialog with: a department picker limited to the departments the current user can manage (use the same list the edition already uses for "departments the user may act in", minus the current one), an optional site (location) picker that reloads with the chosen department, and a confirm step that says in plain words: "The computer's agent and its credential stay the same. It keeps reporting without being reinstalled. Its open alerts, queued jobs, patch and software state and history move to the new department, and technicians of the old department will no longer see it." On confirm, call $module->technician()->transfer($principal, $deviceId, $clientId, $locationId) and show the ActionResult message (success or failure) in the page's normal flash/toast area; on success reload the page at the device in its new department. Do not write your own UPDATE statements and do not move the asset yourself: the Core call moves both. CSRF-protect the POST and write the user-facing strings through the edition's translation layer.

2. Bulk asset transfer. The edition's existing bulk "transfer assets to another department" must route every selected asset that has an endpoint device (an endpoint_agent_devices row with that asset_id) through the same TechnicianActions::transfer() call, one device at a time, collecting the ActionResult of each and reporting how many moved and which were refused (and why: the user lacks manage rights on the old or the new department). Assets without an endpoint device keep today's path. Without this, moving an asset by hand-written SQL orphans the agent's state in the old department. Add a test that bulk-moves an asset with a device and asserts the device row, its jobs and its patch rows end up in the new department and the same device token still checks in.

3. "Managed by another RMM" check box in the installer / enrollment token dialogs. Add it to Download installer, Show deployment commands and Create enrollment token, off by default, label "Managed by another RMM" with the help text: "The computers this installer enrolls are already managed by another RMM or patch tool. RivetIT will monitor them and collect inventory, but will not run scheduled scripts, install patches or deploy software on them. You can change this per computer later." Pass the boolean as the new optional last argument ($managedExternally) of RmmAdmin::downloadInstaller(), RmmAdmin::deploymentCommands() and TechnicianActions::createToken(). If the edition has a REST endpoint that issues an installer or token, accept the optional boolean field `managed_externally` (reject non-boolean values with 422) and pass it through; omitting it must behave exactly as before. On the device page the existing "automation disabled" switch must show the state the token set. Tests: issue with the option, enroll a test device, assert device_automation_disabled = 1 and the Device Automation Disabled audit row; issue without it and assert nothing changed.

4. Bulk action on the device list: with devices selected, offer "Mark as managed by another RMM" and "Clear managed by another RMM" (only to users with rmm.device.manage). Call $module->technician()->setAutomationDisabledBulk($principal, $deviceIds, true|false) (or, for a "whole department" choice, pass the department id as the last argument), cap the selection at 500 in the UI, and after the call show a summary built from ActionResult->message and data['counts']: "N changed, N already set, N skipped" with the skipped computers listed as "not changed: you cannot manage these or they no longer exist" (never say which of the two). Confirm first, saying it stops scheduled scripts, patch installs and software deployment on those computers and cancels queued automated jobs when turned on. Tests: a technician limited to one department selects devices from two; assert only theirs change, the result lists the foreign one as skipped, a second run reports them unchanged, and 501 ids is refused.
```
